## 스펙과 계획을 두는 세 갈래

| 갈래 | 사례 | 스펙 | 계획 |
|---|---|---|---|
| 작업별 날짜 파일 | 이 덱, [superpowers](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/brainstorming/SKILL.md) | `docs/superpowers/specs/<날짜>-<주제>-design.md` | `docs/superpowers/plans/<날짜>-<이름>.md` |
| 층별 폴더 | OpenAI 내부 레포([Harness engineering](https://openai.com/index/harness-engineering/)) | `docs/product-specs/` 기능별 요구 ID | `docs/exec-plans/active`·`completed` |
| 기능별 폴더 | [GitHub spec-kit](https://github.com/github/spec-kit/blob/67e0f7294e6e728ab60bf7b4590deb470448bc2d/spec-driven.md) | `specs/<번호>-<기능>/spec.md` | 같은 폴더의 `plan.md`·`tasks.md` |
| 기능별 폴더 | [Kiro](https://kiro.dev/docs/specs/) | `.kiro/specs/<기능>/requirements.md`·`design.md` | 같은 폴더의 `tasks.md` |
| 없음 | [ghostty](https://github.com/ghostty-org/ghostty/blob/22f100c6367045bb5fc86172f837047dee2f7670/AGENTS.md)·[opencode](https://github.com/anomalyco/opencode/blob/c272a63cb4dd86a3e8771cf9a03be051fae28e95/AGENTS.md)·[tldraw](https://github.com/tldraw/tldraw/blob/12921f6d3996b4330688113371cd88890b673ab5/AGENTS.md) | 이슈 또는 없음 | 없음. AGENTS.md와 검증 명령만 |

**작업별 날짜 파일**은 도구가 만들어 주고 작업별로 남긴다. 프로젝트의 현재 구조·규약은
[프로젝트 설계·규약 문서](/coding-agents/design-docs/)에서 유지하며 새 작업이 참고한다.
**층별 폴더**는 요구 정본이 하나라 여러 계획이 같은 요구를 ID로 가리킨다. superpowers 없이 손으로 운영할 때의
배치이고, 폴더와 ID를 유지하는 비용이 든다. 끝난 계획을 `completed/`로 옮겨 미완료 계획을 폴더로 찾는다.
**기능별 폴더**는 기능 하나의 스펙·계획·작업이 한 폴더에 닫혀 시작이 쉽고 끝나면 통째로 보관된다.
요구가 여러 기능에 걸치면 같은 요구가 여러 폴더에 흩어진다. spec-kit은 전체 원칙을 constitution 파일 하나에,
Kiro는 `.kiro/steering/`에 두어 보완한다.
**없음**도 정상이다. ghostty의 AGENTS.md는 빌드·테스트 명령 위주 200단어 정도이고, opencode는 의존 방향과
코드 스타일 190줄 정도지만 둘 다 계획 문서가 없다. 이슈·PR·대화가 그 역할을 한다.

## superpowers 없이 할 때

superpowers를 설치할 수 없거나 두 도구 중 하나만 쓰는 레포라면 층별 폴더로 같은 효과를 손으로 낸다.
`docs/exec-plans/active/0001-<이름>.md`에 지금 위치·실행 범위·완료 조건·작업·기록 다섯 절을 두고,
도구를 바꾸기 전에 머리의 지금 위치를 갱신하고, 끝나면 `completed/`로 옮긴다. 프로젝트 문서를 참고하고
관련 구현과 함께 갱신하는 원칙, AGENTS.md로 읽을 문서를 연결하는 역할은 두 경우에 같다.

## 실제 레포에서 가져올 것 하나씩

- **tldraw** — [AGENTS.md](https://github.com/tldraw/tldraw/blob/12921f6d3996b4330688113371cd88890b673ab5/AGENTS.md)에 실제 명령과 변경별 검증 범위를 두고, 절차는 `.agents/skills/`로 뺐다. 명령과 검증 범위를 연결하는 방식을 가져온다.
- **VS Code** — Claude 통합 코드 옆의 [Phase 19 계획](https://github.com/microsoft/vscode/blob/d3c24c3c4d7efab36b37acb1e91d9502c0c35b28/src/vs/platform/agentHost/node/claude/phase19-plan.md)은 이전 대화 없는 에이전트를 위한 인계 문서임을 밝히고 목표·제외 범위·실제 검증과 계획에서 달라진 점을 남긴다. 계획과 실행 결과를 한 파일에 잇는 방식을 가져온다.
- **Codex** — 2026-09-30에 루트 AGENTS.md와 `.codex/skills/`를 [레포에서 지웠다](https://github.com/openai/codex/commit/18131270fe). 그 전의 [AGENTS.md](https://github.com/openai/codex/blob/78245b47af2a7aafcabe025828ceecca69db4df1/AGENTS.md)는 검사 이름을 나열하지 않고 어떤 변경에 어떤 검사를 돌리는지 연결했다. 그 연결 방식만 가져온다.

## 내 레포에서 고른다

| 상황 | 고를 것 |
|---|---|
| 같은 요구를 여러 계획이 참조한다 | 층별 폴더 |
| 기능이 서로 독립적이고 한 번에 닫힌다 | 기능별 폴더 또는 이슈 하나 |
| 모든 작업이 한 세션에 끝난다 | 없음. AGENTS.md만 |
| 이미 잘 돌아가는 배치가 있다 | 바꾸지 않는다 |

## Monorepo: 하위 AGENTS.md는 규칙이 갈라지는 곳에만

단일 프로젝트는 루트 AGENTS.md 하나로 충분하다. 앱마다 검사 명령이나 의존 규칙이 달라졌을 때만
그 폴더에 하위 파일을 둔다. 폴더 수가 아니라 규칙의 차이가 경계다.

```md title="apps/web/AGENTS.md"
# web

- 이 지침은 apps/web/에 적용한다.
- 공유 UI는 packages/ui의 기존 컴포넌트를 먼저 확인한다.
- src/server 모듈을 브라우저 코드에서 import하지 않는다.
- 동작 변경은 pnpm --filter web test로 검증한다.
```

- 하위 파일은 상위를 복사하지 않고 그 범위의 차이만 적는다. 루트에 "모든 package는 Jest", web에 "Vitest"라고 쓰면 충돌한다.
- 두 도구 모두 작업 디렉터리 아래의 지침은 시작 때 읽지 않는다([읽는 조건](/coding-agents/agents-md/#두-도구가-읽는-조건)). 루트의 "하위 AGENTS.md를 수정 전에 읽는다" 조건이 이 파일을 읽게 한다.
- 어느 폴더에도 CLAUDE.md가 남아 있지 않은지 본다. 있으면 그 범위의 AGENTS.md가 무시된다.

## 이해 확인

기능별 폴더로 시작한 레포에서 세 번째 기능이 첫 기능의 요구를 다시 적고 있다. 어떻게 할까?
그 요구를 층별 정본으로 한 번 빼고 두 폴더가 ID로 가리키게 한다. 전체 구조를 한 번에 바꿀 필요는 없다.

web과 api의 규칙이 같은데 폴더가 둘이다. 하위 AGENTS.md가 둘 다 필요할까? 필요 없다.
공통 규칙으로 충분한 동안은 루트만 유지하고, 실제 차이가 생긴 경계에 추가한다.
