## 아이디어와 해결 방향을 탐색한다

아직 어떤 방향을 택할지 열려 있을 때 쓴다. 대괄호에 아는 내용을 넣고, 모르는 것은 모른다고 적는다.

```text
[사용자]가 [상황에서 겪는 문제]를 해결할 제품 아이디어를 탐색해 줘.
현재 대안은 [대안], 이미 확인한 근거와 자료는 [내용·실제 경로]야.
이번에 결정할 것은 [해결 방향 또는 먼저 시험할 후보]야.
pm-product-discovery의 적절한 스킬로 후보·가정·우선 확인할 실험을 정리해 줘.
각 판단의 근거와 아직 모르는 것을 구분하고 결과를 저장한 실제 경로를 알려 줘.
이번에는 탐색 결과까지만 정리하고 PRD·개발 설계·구현은 시작하지 마.
```

**받을 결과:** 후보와 선택 이유, 중요한 가정, 그 가정을 확인할 실험과 판단 기준이다.
이 흐름은 [discover 원문](https://github.com/phuryn/pm-skills/blob/07b34f64ee828df08953f505b7f747aef85ae7c6/pm-product-discovery/commands/discover.md)의
탐색·가정·실험 설계를 자연어로 요청한 것이다. 스킬의 질문이나 양식을 미리 복제할 필요는 없다.

| 결과에서 확인할 것 | 판단할 기준 |
|---|---|
| 후보와 선택 이유 | 사용자 문제·현재 대안·제약과 연결되는가 |
| 핵심 가정과 근거 | 관찰한 사실과 AI의 추정이 구분되는가 |
| 실험과 판정 기준 | 무엇을 측정하고 어느 결과에서 진행·수정·중단할지 알 수 있는가 |
| 실제 확인 범위 | 실험을 설계한 것과 실행해 결과를 얻은 것을 구분하는가 |

예를 들어 “보고서 준비가 느리니 CSV 내보내기가 필요하다”는 해결 방향이다. 병목이 데이터 추출인지
수작업 정리인지 아직 모르면 사용자 과정을 관찰하는 실험부터 제안할 수 있다.
그 실험을 문서로 정했다고 병목이나 수요가 검증된 것은 아니다. 인터뷰·실험 실행·외부 반영은 별도 요청 범위를 따른다.
이미 요구가 확정된 기능 개발이나 버그 수정은 이 탐색을 반복하지 않고 [개발 요청](/coding-agents/workflow/)으로 간다.

탐색부터 PRD까지 맡기려면 위 요청의 마지막 문장을 다음으로 바꾼다.

```text
탐색에서 선택한 방향과 근거·남은 가정을 create-prd에 넘겨 첫 PRD까지 작성해 줘.
새 PRD는 docs/product-specs/PRD-[product-name].md에 저장하고 탐색 결과의 실제 경로를 연결해 줘.
이번에는 제품 문서까지만 준비하고 개발 설계·계획·구현은 시작하지 마.
```

create-prd에 필요한 제품 맥락이 부족하면 작성 전에 질문한다.
탐색 결과를 전부 PRD에 복제하거나 별도 고정 파일명·양식을 만들지 않는다.

## 첫 PRD를 작성한다

제품 방향이 정리됐고 PRD가 없을 때 쓴다. 새 프로젝트 세팅에서 이미 작성했다면
[같은 파일을 리뷰](/coding-agents/product-requirements/#기존-prd를-리뷰한다)한다.
아래는 제품 이름을 task-manager로 정한 가상의 업무 서비스 예시다.

```text
pm-execution의 create-prd로 첫 PRD를 작성해 줘.
대상 사용자는 [사용자], 문제와 확인한 근거는 [내용], 현재 대안은 [대안]이야.
성공 여부는 [측정할 결과와 조건], 첫 버전 범위는 [포함], 제외할 것은 [제외]야.
관련 탐색 결과가 있으면 [실제 경로]를 읽고 근거·남은 가정을 이어받아 줘.

스킬의 양식으로 docs/product-specs/PRD-task-manager.md에 저장해 줘.
이번에는 제품 문서까지만 작성하고 개발 설계·계획·구현은 시작하지 마.
```

**받을 결과:** 첫 버전을 결정할 수 있는 짧은 PRD와 의도적으로 생략한 내용에 대한 안내다.
사용자 문제·첫 범위·성과 기준이 맞물리는지, 근거 없는 사용자 의견·성과 수치를 사실처럼 넣지 않았는지 본다.

[create-prd 원문](https://github.com/phuryn/pm-skills/blob/07b34f64ee828df08953f505b7f747aef85ae7c6/pm-execution/skills/create-prd/SKILL.md)은
문제·대상 사용자·성공 기준이 부족하면 먼저 질문하고 그 응답에서는 PRD를 쓰지 않게 한다.
사용자가 그대로 진행하라고 지시한 경우에만 공백을 가정으로 표시해 작성한다.
나머지 미확인 내용도 사실로 채우지 않고 스킬의 가정·열린 질문에 남긴다.

파일명 `PRD-[product-name].md`와 내용 구성은 스킬이 정한다. 이 덱은 **새 PRD의 보관 폴더만
`docs/product-specs/`로 지정**한다. 별도 제품 README나 요구 ID·상태 관리 양식을 만들 필요는 없다.

## 기존 PRD를 리뷰한다

`docs/prd.md`에 기존 PRD가 있다고 가정한 **리뷰만** 요청하는 예시다.
자기 프로젝트의 실제 파일 경로로 바꾼다.

```text
create-prd로 docs/prd.md를 리뷰해 줘.
첫 버전을 결정하는 데 빠진 내용을 먼저, 줄여도 될 내용을 다음으로 알려 줘.
제품 목적·범위·정책 변경은 이유와 영향을 제안으로 남겨 줘.
파일 수정·새 PRD 작성·개발은 하지 말고 리뷰 결과에서 멈춰 줘.
```

**받을 결과:** 결정을 막는 누락과 줄일 내용의 제안이다. 파일은 바뀌지 않는다.
이는 create-prd의 기존 PRD 리뷰 기준을 따른다. 사용자와 가치·해결 범위·성과 기준이 연결되는지,
가정을 사실처럼 쓰지 않았는지 확인한다. 제안이 나왔다는 이유로 제품 결정이 확정된 것은 아니다.

### 리뷰와 문서 교정을 함께 맡긴다

아래는 **같은 파일의 문장·링크 교정까지 허용**하는 예시다.

```text
create-prd로 docs/prd.md를 리뷰해 줘.
결정을 막는 누락을 먼저, 줄일 수 있는 내용을 다음으로 제안해 줘.
수정은 docs/prd.md 안의 오탈자·의미를 유지하는 문장 교정과
파일 이동으로 깨진 내부 링크의 실제 경로 교정에 한정해 줘.
제품 목적·범위·정책이나 수치를 바꾸는 내용은 반영하지 말고 제안으로 남겨 줘.
새 PRD나 사본을 만들지 말고 원래 위치에 반영한 수정 내역을 보고해 줘.
개발은 시작하지 마.
```

**받을 결과:** 리뷰 제안과 실제 교정 내역이 구분된 보고다.
수정 대상 파일·문장이나 링크가 명시되고 허용한 범위를 지켰는지 diff와 대조한다.
예를 들어 문장이 어색하다고 CSV 한도 1,000건을 5,000건으로 바꾸는 것은 교정 범위 밖이다.
제품 요구 변경은 [변경하고 이어받기](/coding-agents/updates-and-handoff/)의 요청으로 따로 다룬다.

## 확정된 요구를 개발로 넘긴다

기획만 맡겼다면 여기서 제품 결정을 확인하고 멈춘다. 개발까지 맡길 준비가 됐을 때
PRD의 실제 경로와 이번 구현 범위를 전달한다.

```text
docs/product-specs/PRD-task-manager.md의 CSV 내보내기를 구현하려고 해.
첫 한도는 1,000건이며 조회 권한·필터를 유지하고,
1,001건부터는 파일 대신 제한 안내를 보여 주는 범위야.
현재 문서와 코드를 읽고 superpowers로 개발 설계·계획을 작성한 뒤 실행 전에 멈춰 줘.
설계에 관련 PRD와 이번 범위를 연결하고 이미 정한 제품 결정을 전제로 다뤄 줘.
바꿔야 할 제품 목적·범위·정책이 있으면 이유와 영향을 먼저 제안해 줘.
```

**받을 결과:** 제품 요구를 입력으로 삼은 개발 설계와 구현·검증·문서 갱신 계획이다.
PRD를 검토한 것이 기술 설계·계획의 승인까지 뜻하지는 않는다.
[개발 맡기고 결과 확인하기](/coding-agents/workflow/)에서 접근법·설계 승인과 계획 리뷰·확인을 이어 간다.

수용 기준을 통과한 것과 사용자 문제가 해결된 것도 따로 확인한다.
CSV 다운로드 테스트가 통과해도 보고서 준비 시간이 줄었는지는 실제 사용자 과제로 관찰해야 한다.
관찰하지 않은 성과는 검증 완료로 보고하지 않는다.
