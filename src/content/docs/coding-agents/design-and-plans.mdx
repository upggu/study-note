## 작업별 설계와 계획

작업별 spec은 관련 PRD·현재 기술 문서·코드를 읽은 결과에서 출발한다. 가상 CSV 내보내기라면
조회 권한·필터 적용, 1,000건 한도와 초과 시 안내, 비동기 처리를 첫 범위에서 제외한 이유가 설계의 입력이다.
완료 조건은 **어떤 입력에서 무엇을 관찰하면 통과인가**로 읽는다. 권한 있는 업무가 25건이고 화면이
10건씩 보여도 CSV에는 25건이 들어가야 한다. 파일 다운로드 성공만으로 이 요구를 확인할 수 없다.

설계·계획의 세부 구성과 파일 생성 여부는 설치된
[brainstorming](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/brainstorming/SKILL.md)·
[writing-plans](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/writing-plans/SKILL.md)를 따른다.
설계가 필요한 변경은 검토·승인을 거쳐 계획으로 넘긴다. Codex 설치본 7.0.1과 Claude Code 설치본 7.0.0의
작은 변경 처리까지 같다고 가정하지 않는다. 사용하는 도구의 스킬 원문으로 판단한다.

예시의 사전 지정된 실행 선호와 실제 도구 조건은
[연결 규칙](/coding-agents/project-setup/#ai가-적용할-연결-규칙)에서 확인한다.
실행 방식이 정해져 있어도 계획 리뷰와 확인은 유지된다.
하위 에이전트 도구가 없어 `executing-plans`로 직접 실행한다면 독립 리뷰를 했다고 보고하지 않는다.
설치된 스킬은 이 경우 최종 self-review와 그 한계 보고를 안내한다
([executing-plans의 Final Review](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/executing-plans/SKILL.md#final-review)).
도구가 있는데 직접 실행을 선택한 경우와 도구가 없는 경우도 구분한다.

## 현재 기술 문서는 다음 작업의 기준이다

CSV를 만들 때 정한 수식 주입 방지 방법이 옛 spec이나 ledger에만 있으면 다음 CSV 기능을 맡은 세션은
같은 결정을 다시 찾게 된다. 현재 모듈 책임과 출력 규약을 기술 문서에 반영하고 AGENTS.md에서 읽을 조건을 연결한다.

새 프로젝트의 현재 구조·실행 정보는 README에 두고, 기존 프로젝트는 이미 쓰는 기술 문서를 유지한다.
별도 문서가 필요할 때 실제 주제로 연결한다. 아래는 `docs/design-docs/csv-output.md`가 있는 프로젝트의
설명용 예시이며, 파일 배치나 HTTP 상태를 모든 프로젝트에 요구하는 규칙은 아니다.

```md title="docs/design-docs/csv-output.md"
# CSV 구조와 출력 규약

제품 동작은 ../product-specs/PRD-task-manager.md의 CSV 내보내기 요구를 따른다.
첫 적용 설계: ../superpowers/specs/2026-10-24-csv-export-design.md

## 구조와 데이터 흐름

- apps/web은 필터를 apps/api에 전달하고 반환된 CSV를 다운로드한다.
- apps/api는 사용자의 조회 권한과 필터를 적용해 DB에서 항목을 읽는다.
- 목록 API와 CSV API는 권한·필터 처리를 공유한다. 화면 페이지 제한은 목록 API에서만 적용한다.
- packages/csv는 조회된 항목을 CSV로 변환한다. DB 조회와 권한 판단은 맡지 않는다.

## 출력 규약

- 생성은 packages/csv의 toCsv()를 사용한다.
- 셀 값이 =·+·-·@로 시작하면 앞에 작은따옴표를 붙인다.
- 이 예시 API는 한도를 넘으면 CSV 대신 413과 제한 안내를 반환한다. 현재 한도는 PRD를 따른다.

## 선택 이유

- 화면 목록 함수 안에 페이지 제한이 있어 그대로 재사용하지 않았다. 권한·필터 부분을 분리해 공유한다.
- 첫 요구가 1,000건 이하라 비동기 처리를 도입하지 않았다. 한도 변경 시 성능과 처리 방식을 재검토한다.
```

출력 규약은 이 가상 예제에서 정한 선택이다. 실제 적용 시 사용하는 스프레드시트·출력 형식과 검증 결과를
확인한다. 문서에는 구조·적용 범위·결정 이유를 적고 세부 계약은 코드·테스트로 연결한다.
타입·lint가 검사하는 규칙을 모두 복사하지 않는다.

## 구현과 함께 현재 문서를 갱신한다

| 시점 | CSV 예시에서 할 일 |
|---|---|
| 작업 시작 | AGENTS.md가 가리키는 PRD·CSV 기술 문서와 코드를 읽고 이번 설계의 전제로 사용 |
| 구현과 수정 | 권한·필터 처리의 위치를 바꾸면 현재 데이터 흐름과 연결 경로를 같은 작업에서 갱신 |
| 최종 리뷰 전 | 1,000건에서 5,000건으로 승인된 변경이 PRD·검증·기술 문서에 맞는지 대조. 미출시면 상태도 구분 |
| 결정 변경 | 현재 기준은 새 결정으로 고치고, 남길 옛 이유는 대체된 결정임을 표시 |

제품 목적·범위·정책 변경은 사용자 결정이 필요하다. 허용한 수정만 기존 문서에 반영하며,
완료된 옛 spec을 현재 구조 문서처럼 계속 고치지 않는다.
자세한 요청 범위와 1,000→5,000건 예시는 [변경 요청](/coding-agents/updates-and-handoff/#제품-요구를-바꾼다)을 본다.

## 진행 기록으로 실제 상태를 대조한다

예를 들어 ledger에 “CSV 변환 완료, 25건 확인”이라고 적혀 있어도 이후 API의 조회 코드가 바뀌었다면
그 결과가 지금 코드의 통과 증거는 아니다. 기록이 가리키는 코드 상태와 현재 변경을 대조하고,
영향받은 검증이 필요한지 판단한다. 계획의 체크 표시나 폴더 유무만으로 완료를 정하지 않는다.

ledger의 위치와 계획 연결은 [폴더 구조](/coding-agents/project-structure/#어느-경로를-그대로-따르는가)를,
기록이 없거나 다른 clone·worktree에서 넘겨받을 때는
[변경하고 이어받기](/coding-agents/updates-and-handoff/#같은-작업-폴더에서-재개한다)를 따른다.

## ledger가 삭제되기 전에 결정을 옮긴다

실행 스킬은 최종 리뷰 뒤 workspace를 정리하고 finishing 단계로 넘긴다.
다음 작업에도 필요한 결정은 **관련 구현을 바꾸는 작업 안에서, 최종 리뷰와 삭제 전에** 옮긴다.

| ledger에서 발견한 내용 | 남길 곳 |
|---|---|
| CSV 한도와 초과 시 사용자 안내 | 현재 PRD |
| 수식 주입 방지 방식·권한/필터 공유 구조와 이유 | 현재 기술 문서 |
| Task에서 어느 함수를 고쳤는지, 임시 시행착오 | 진행 기록에 남김. 지속 문서에 모두 복사하지 않음 |

finishing까지 기다리면 임시 기록이 사라질 수 있다.
커밋·외부 반영은 프로젝트의 기존 정책과 사용자 허용 범위 안에서 처리한다.
구현·검증 완료를 실제 출시 완료로 표현하지 않는다.

## 이해 확인

새 기능이 CSV 모듈 위치를 바꿨다면 옛 spec만 고칠까? 현재 기술 문서와 관련 링크를 함께 고친다.
옛 spec·plan은 당시 기록으로 남긴다.

다른 clone의 계획을 이어받는데 ledger가 없다면 처음부터 할까? 실제 코드·이력·diff·검증과
원래 폴더의 진행 기록을 대조해 끝난 작업부터 확인한다.

하위 에이전트 도구 없이 직접 검토했다면 독립 리뷰 완료일까? self-review로 표시하고 확인의 한계를 보고한다.
