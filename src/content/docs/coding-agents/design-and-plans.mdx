## 세 파일이 생기는 순서

| 파일 | 만드는 skill | 언제 | 커밋 |
|---|---|---|---|
| `docs/superpowers/specs/<날짜>-<주제>-design.md` | brainstorming | 설계가 필요한 변경의 접근법을 정한 뒤. 작은 변경은 짧게, 프로젝트는 상세하게 작성 | 한다 |
| `docs/superpowers/plans/<날짜>-<기능>.md` | writing-plans | 설계를 승인한 뒤 | 한다 |
| `.superpowers/sdd/<계획 이름>/progress.md` | subagent-driven-development 또는 executing-plans | 계획 실행을 시작할 때 | 기본은 안 한다 |

brainstorming v7.0.1은 "아이콘을 파랗게"처럼 필요한 내용이 모두 정해진 요청은 바로 처리한다.
설계가 필요한 변경은 접근법을 고른 뒤 작은 변경이면 짧은 설계 문서를, 프로젝트면 상세한 설계 문서를
작성한다. 둘 다 승인을 받은 뒤 writing-plans로 넘어간다
([brainstorming](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/brainstorming/SKILL.md)).

**이 덱의 운영 원칙은 작은 수정에 별도 설계·계획 파일을 만들지 않는 것이다.**
[AGENTS.md 템플릿](/coding-agents/agents-md/#템플릿)에 이 예외를 명시한다.
위 표는 파일을 만드는 작업의 절차이며, 파일 생략은 superpowers의 크기 판정만으로 보장되는 동작이 아니다.
사용자 요청과 AGENTS.md가 skill보다 우선한다는 규칙에 따라 적용한다
([using-superpowers](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/using-superpowers/SKILL.md)).

## 설계: 무엇을 왜

작업별 설계(spec)는 관련 프로젝트 문서와 코드를 읽은 결과에서 출발한다. "이 분야의 유능한 빌더가
사용자에게 되묻지 않고 계획을 세울 수 있는 문서"다.
의도와 이유, goals·non-goals, 제약, **검토한 접근법 2~3개와 고른 이유**, 사용자가 정한 것과 빌더에게
맡긴 것을 담는다. 가상 CSV 내보내기라면 "권한과 화면 필터를 그대로 적용, 최대 1,000건, 초과 시 안내,
비동기 내보내기는 non-goal" 같은 내용이다. 완료 조건의 정본이므로 요구가 바뀌면 이 파일을 먼저 고친다.

완료 조건에는 **어떤 입력에서 무엇을 관찰하면 통과인가**를 적는다. 예를 들어 조회 권한이 있고 필터에 맞는
업무 25건과 조회 권한이 없는 다른 사용자의 업무를 준비한다. 화면은 10건씩 표시해도 CSV에는 권한 있는
25건이 모두 들어 있고, 권한 밖 업무는 없어야 한다. 파일이 내려받아졌어도 10건뿐이면 실패다.
설계를 승인할 때 이 조건이 있는지 보고, 구현 뒤에는 같은 입력으로 다운로드한 결과와 대조한다.

## 계획: 어떤 순서로

계획은 "이 코드베이스를 본 적 없는 엔지니어가 그대로 따를 수 있는 작업 목록"이다. 머리에 Goal·Architecture·
**Spec 경로**·전역 제약이 있고, 작업마다 만들 파일·인터페이스·단계(실패 테스트 작성 → 실패 확인 → 구현 →
통과 확인 → 커밋)가 체크박스로 있다
([writing-plans](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/writing-plans/SKILL.md)).

계획이 끝나면 superpowers가 실행 방식을 묻는다. 작업마다 새 subagent가 구현하고 또 다른 subagent가
리뷰하는 **subagent-driven**이 기본 추천이고, 한 세션에서 직접 구현하고 마지막에 한 번 리뷰하는
**native**(executing-plans)가 싼 대안이다. 둘 다 같은 ledger를 쓰므로 중간에 바꿔도 이어진다.

작업 중 요구가 바뀌면 해당 spec을 고치고 plan을 맞춘다. 구조·규약을 바꾸는 작업에는 관련 프로젝트 문서
갱신도 넣는다. 완료된 spec·plan은 당시 기록으로 보존하고, 이후 변경은 새 작업에서 다룬다.

## 진행 기록: 지금 어디까지

실행 skill은 계획마다 `.superpowers/sdd/<계획 이름>/`를 만들고 `progress.md`에 적는다.

```text title=".superpowers/sdd/2026-10-24-csv-export/progress.md"
# SDD ledger — plan: docs/superpowers/plans/2026-10-24-csv-export.md
Pre-flight: no shared interfaces
Task 1: complete (commits 3f2a9c1..8b77d04, tests: pnpm --filter api test → 12 passed)
Task 2: Ruling: listTasks()는 페이지 제한이 안에 있어 재사용 불가 — 권한·필터 부분을 분리해 공유 — 틀리면 조회 결과가 화면과 달라짐
Task 2: complete (commits 8b77d04..c01e5aa, tests: pnpm --filter api test → 15 passed)
```

첫 줄이 어느 계획의 기록인지, `Task N: complete` 줄이 어디까지 끝났는지, `Ruling:` 줄이 실행 중 내린
결정과 이유를 말한다. 새 세션은 이 파일과 `git log`를 자기 기억보다 믿고, 완료된 작업은 다시 하지 않는다
([executing-plans](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/executing-plans/SKILL.md)).

**실행 기록을 찾을 때**는 현재 작업 폴더의 `.superpowers/sdd/`를 본다.

```bash
ls .superpowers/sdd/
```

폴더가 없으면 아직 실행하지 않았거나, 다른 clone·worktree에서 실행 중이거나, 최종 리뷰 뒤 삭제된 것일 수 있다.
폴더가 남아 있어도 중단된 옛 기록일 수 있다. 계획·ledger가 가리키는 코드 상태와 `git log`·`git diff`·검증 결과를
대조해 완료한 작업과 남은 작업을 판단한다. 폴더 유무만으로 완료를 정하지 않는다.

## 다른 작업 폴더로 넘길 때

superpowers는 `.superpowers/sdd/.gitignore`에 `*`를 써서 workspace 전체를 Git에서 뺀다. 두 도구가
**같은 작업 폴더**를 열면 같은 ledger를 읽는다. 같은 기기의 다른 clone·worktree도 별도 폴더이므로,
코드·미커밋 변경과 함께 ledger를 전달해야 한다
([workspace 경로 구현](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/subagent-driven-development/scripts/sdd-workspace)).

ledger를 복사해 전달할 수 있다. Git으로 전달하려면 아래 설정으로 커밋 대상에 넣는다. 이 `.gitignore`는 이미 있으면
덮어쓰지 않으므로(v7.0.0부터) 레포가 직접 둘 수 있다. 작업 요약·리뷰 패키지는 계속 제외된다.

```text title=".superpowers/sdd/.gitignore"
*
!*/
!*/progress.md
!.gitignore
```

Git으로 전달할 때는 커밋·원격 전송에 관한 레포 정책을 따른다. 받는 쪽에도 해당 코드와 ledger가 도착했는지
확인한다. `.gitignore`를 바꾸거나 로컬에서 커밋한 것만으로 다른 clone에 전달되지는 않는다.

## ledger가 삭제되기 전에 결정을 옮긴다

superpowers의 실행 skill은 최종 리뷰를 마친 뒤 workspace를 삭제하고 finishing-a-development-branch로
넘어간다. finishing은 테스트를 돌리고 merge·PR·보류 등을 묻는다
([실행 순서](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/executing-plans/SKILL.md)).
따라서 이 덱에서 더하는 프로젝트 문서 갱신은 **관련 구현을 바꾸는 작업 안에서, 최종 리뷰 전에** 수행한다.
다음 작업에도 적용될 결정(CSV 수식 주입 방지 방식, 조회 함수 분리 같은 것)이 설계 파일이나 ledger에만 있으면
[프로젝트 설계·규약 문서](/coding-agents/design-docs/)로 옮긴다. 설계·계획 파일은 남지만 ledger는 삭제되므로,
finishing 단계까지 기다리면 ledger에만 있던 결정을 잃을 수 있다.

## 이해 확인

`docs/superpowers/plans/`에 파일이 셋인데 `.superpowers/sdd/`가 없다. 모두 완료됐을까? 아직 실행하지 않은
계획일 수도 있다. 각 계획의 작업을 실제 코드·변경 이력·검증 결과와 대조하고, 다른 작업 폴더에 기록이 있는지도 확인한다.

동료의 clone에서 계획을 이어받았는데 `.superpowers/sdd/`가 비어 있다. 처음부터 다시 할까? 아니다.
계획과 `git log`·`git diff`를 대조해 완료한 작업을 확인하고, 원래 작업 폴더의 미커밋 변경과 ledger도 챙긴다.
같은 기기라도 작업 폴더가 다르면 자동으로 따라오지 않는다.
