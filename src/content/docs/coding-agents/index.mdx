<Thesis>

- PM Skills는 만들 가치와 범위를 검토하고, superpowers는 합의한 요구를 설계·구현·검증으로 이어 가도록 돕는다.
- 스킬은 반복해서 쓸 질문과 작업 절차를 제공한다. 매번 긴 요청문으로 그 절차를 다시 설명하는 부담을 줄인다.
- 상황에 맞는 요청문을 쓰고, AI가 돌려준 제품 결정·설계·검증 결과를 확인한다.
- 이 덱은 문서 보관 위치, 기존 문서 연결, 스킬 사이의 인계와 지속 문서 갱신을 더한다.
- 기획만 요청하면 기획에서 멈춘다. 합의된 요구의 개발에 제품 탐색을 반복하지 않는다.

</Thesis>

AI에게 기능을 맡겼는데 무엇을 만들기로 했는지 다시 설명하거나, 새 세션이 끝난 작업을 반복할 수 있다.
**제품의 목적과 결정을 문서로 연결하고, 그 문서를 읽어 개발하게 하면** 다음 요청도 같은 기준에서 시작할 수 있다.

이 덱은 Git·Markdown·기본 명령 실행을 아는 사람이 Codex 또는 Claude Code로 자신의 프로젝트를
기획하고 개발하도록 돕는다. 둘 중 하나만 써도 된다. 예시는 가상 업무 서비스의 CSV 내보내기다.

## 왜 PM Skills와 superpowers를 쓰는가

“CSV 내보내기를 만들어 줘”라는 요청만으로는 누구에게 왜 필요한지, 어느 데이터를 내보낼지,
무엇을 확인해야 완료인지가 빠질 수 있다. AI와 매번 대화로 정할 수도 있지만,
**반복해서 확인할 질문과 절차를 스킬로 불러 쓰면** 요청마다 같은 점검 방법을 다시 설명할 필요가 줄어든다.
스킬은 AI가 읽고 따르는 작업 지침이며, 제품 판단과 결과 확인은 사용자가 맡는다.

| 빠지기 쉬운 판단 | 사용하는 스킬 | 도움을 받는 방식 |
|---|---|---|
| 이 기능이 실제 문제를 푸는가 | PM Skills의 [pm-product-discovery](https://github.com/phuryn/pm-skills/blob/07b34f64ee828df08953f505b7f747aef85ae7c6/pm-product-discovery/commands/discover.md) | 해결 방향을 비교하고, 아직 근거가 없는 가정과 먼저 해 볼 실험을 구분한다 |
| 누구에게 무엇을 어디까지 제공할 것인가 | pm-execution의 [create-prd](https://github.com/phuryn/pm-skills/blob/07b34f64ee828df08953f505b7f747aef85ae7c6/pm-execution/skills/create-prd/SKILL.md) | 사용자·문제·성과 기준·첫 범위를 제품 요구사항 문서(PRD)로 정리해 개발의 입력으로 남긴다 |
| 합의한 요구를 어떻게 만들고 완료를 확인할 것인가 | [superpowers](https://github.com/obra/superpowers/tree/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills) | 접근법과 설계를 검토하고 구현 계획·테스트·리뷰·진행 기록으로 실행과 확인을 이어 간다 |

CSV 예시에서 PM Skills로 먼저 따질 것은 “보고서 준비가 느린 원인이 데이터 추출인가”와
“CSV가 적절한 해결책인가”다. 필요성이 확인되어 첫 범위를 합의했다면 PRD에 조회 권한·화면 필터·1,000건 한도를 남긴다.
superpowers로는 그 요구를 구현할 데이터 흐름을 설계하고, 1,000건 다운로드와 1,001건 제한 안내 등을 검증한다.
실험을 제안한 것과 필요성을 확인한 것, 코드를 만든 것과 검증한 것을 각각 구분할 수 있어야 한다.

두 스킬을 연결하는 이유는 **제품에서 합의한 내용이 개발과 검증의 기준으로 이어지게 하려는 것**이다.
superpowers도 요구를 질문하고 설계를 다듬지만, 이 덱은 제품 문제·대안·성과의 검토를 PM Skills에 맡기고
합의한 PRD를 개발 설계에 연결한다. 문서의 실제 경로와 갱신 조건은
[프로젝트 연결 규칙](/coding-agents/project-setup/#ai가-적용할-연결-규칙)으로 보완한다.

## 모든 작업에 둘 다 필요한가

제품 방향을 탐색하고 여러 작업·세션에 걸쳐 개발할 때 이 흐름을 적용할 이유가 크다.
반면 이미 합의한 요구의 버그 수정은 기존 PRD를 읽고 개발 절차로 들어가면 된다.
오탈자처럼 범위가 분명한 수정에 제품 탐색이나 새 PRD부터 반복하지 않는다.
변경 규모에 따른 설계·계획 처리는 설치된 스킬의 조건을 따른다.

스킬 없이도 같은 질문·설계·검증을 수행할 수 있다. 이 조합을 쓰는 이유는 그 작업 방식을 재사용하기 위해서다.
질문과 리뷰에는 시간과 토큰이 들며, 설치만으로 제품의 성공이나 코드의 정확성이 보장되지는 않는다.
기존 절차로 충분한 작업까지 새 문서를 늘리지 않고, 현재 부족한 판단이나 확인에 필요한 스킬을 쓴다.

**설치 → 프로젝트 적용 → 제품 기획 → 개발 → 갱신·이어받기**로 이어진다.
이미 마친 준비는 반복하지 않고 지금 맡길 작업에서 시작한다.

| 프로젝트에 연결한다 | [프로젝트에 적용하기](/coding-agents/project-setup/) | 기존 문서·명령·지침을 연결한다. 신규 세팅은 요청에 따라 문서 또는 실행 환경까지 준비한다 |
| 아이디어를 탐색하거나 PRD를 정리한다 | [제품 기획과 PRD 리뷰 맡기기](/coding-agents/product-requirements/) | 후보·가정·근거를 확인하고 제품 문제·첫 범위·성과 기준을 정한다 |

## 근거와 확인 범위

스킬의 양식·파일명·개발 절차는 설치된 원문을 따른다. 이 조합과 문서 갱신은 덱의 운영 방식이다.
스킬 사이의 자동 동기화 기능을 뜻하지 않는다.
제품 목적·범위·정책 결정과 스킬이 요청하는 설계·계획 검토·승인은 사용자가 맡는다.

2026-10-25에 Codex superpowers 7.0.1,
Claude Code superpowers 7.0.0, 양쪽 pm-execution 2.2.0 설치본을 읽었다.
pm-product-discovery 2.2.0은 marketplace 체크아웃 원문을 확인했다.
이 열람을 새 세션의 자동 발견·전체 실행 성공으로 해석하지 않는다.
