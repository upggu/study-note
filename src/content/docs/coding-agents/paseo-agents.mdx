## 앱·daemon·코딩 에이전트

앱에서 요청을 보내면 daemon이 실제 호스트의 코딩 에이전트를 실행하는 구조다.

```d2 sketch=false title="Paseo 앱은 daemon에 연결하고 daemon은 호스트의 코딩 에이전트를 실행한다"
direction: down
classes: {
  key: { style: { fill: "#dbeafe"; stroke: "#2563eb"; font-color: "#1e3a8a" } }
  mute: { style: { fill: "#f1f5f9"; stroke: "#94a3b8"; font-color: "#334155" } }
}
app: "Paseo 앱\n데스크톱·모바일·웹"
host: "에이전트 실행 호스트" {
  daemon: "Paseo daemon\n세션·workspace 관리" { class: key; style.stroke-width: 4 }
  provider: "provider 연결\n실행·입출력 처리"
  agent: "코딩 에이전트\n설치된 CLI 프로세스"
  files: "workspace의 코드 파일" { class: mute }
  daemon -> provider
  provider -> agent: 실행·입출력
  agent -> files: 읽기·수정·검증
}
app -> host.daemon: 요청·상태 확인
```

- **앱:** 대화·상태·diff·터미널을 보여 주는 사용자 인터페이스다.
- **daemon:** 로컬 또는 원격 호스트에서 에이전트와 작업 공간을 관리한다.
- **provider:** 설치·인증된 코딩 에이전트를 실행하고 입력·출력·모드를 연결한다.
- **코딩 에이전트:** 자기 도구로 파일을 편집하고 명령을 실행한다. 모델 추론은 해당 provider의 연결을 따른다.
- **파일 위치:** 코드·CLI·인증은 에이전트가 실행되는 호스트에 있다. 모바일에서 접속해도 모바일 안에서 빌드하는 것은 아니다.

근거: [Providers](https://paseo.sh/docs/providers.md), [연결 구조](https://paseo.sh/docs/connectivity.md).

## 내부적으로 MCP가 동작하는가

- **그렇다.** Paseo는 에이전트·workspace 관리 기능을 제공하는 MCP 서버를 갖는다.
- **모든 경로가 MCP인 것은 아니다.** provider에 따라 같은 기능을 native 도구 인터페이스로 제공하기도 한다.
- **MCP의 역할:** `create_agent` 같은 도구 호출을 Paseo 기능으로 연결한다. 모델을 직접 실행하거나 작업을 스스로 분배하지 않는다.
- **작업 분배의 주체:** 도구 설명과 요청을 읽은 주 에이전트가 호출할 도구·인수·작업 내용을 정한다.

```d2 sketch=false title="에이전트의 Paseo 도구 호출은 MCP 또는 native 인터페이스를 통해 관리 기능에 도달한다"
direction: down
classes: {
  key: { style: { fill: "#dbeafe"; stroke: "#2563eb"; font-color: "#1e3a8a" } }
}
lead: "주 에이전트\nPaseo 도구 호출"
mcp: "MCP 서버 경로" { class: key; style.stroke-width: 4 }
native: "native 도구 경로"
service: "Paseo 관리 기능\n에이전트·workspace·상태"
lead -> mcp: MCP로 제공하는 provider
lead -> native: native로 제공하는 provider
mcp -> service
native -> service
```

| 설정 | 기본값 | 의미 |
|---|---|---|
| `daemon.mcp.enabled` | `true` | MCP 서버 실행 |
| `daemon.mcp.injectIntoAgents` | `false` | Paseo가 실행한 에이전트에 도구 제공 |

- **사용 설정:** `Settings → 해당 host → Agents → Enable Paseo tools`를 켠 뒤 새 에이전트를 시작하거나 reload한다.
- **구현 근거:** `mcp-server.ts`는 MCP SDK로 서버를 만들고 공통 도구 목록을 등록한다.
- **MCP 연결 경로:** `runtime-mcp-config.ts`는 `paseo`라는 HTTP MCP 설정과 호출자 에이전트 ID를 런타임에 연결한다. native 경로 전체를 이 HTTP 경로로 해석하면 안 된다.
- **CLI도 가능:** 셸을 쓸 수 있는 에이전트는 Paseo CLI로 조율할 수 있다. 이 경로는 MCP 도구 주입을 켜야만 가능한 것은 아니다.

근거: [MCP 설정](https://paseo.sh/docs/mcp.md#configuration), [MCP 서버 코드](https://github.com/getpaseo/paseo/blob/main/packages/server/src/server/agent/mcp-server.ts), [런타임 연결 코드](https://github.com/getpaseo/paseo/blob/main/packages/server/src/server/agent/runtime-mcp-config.ts), [CLI 경로](https://paseo.sh/docs/orchestration.md#cli).

## 위임 요청 한 번의 흐름

`create_agent`의 응답은 작업 완료가 아니라 **새 에이전트의 식별자**다. 완료 알림은 나중에 도착한다.

```d2 pad=40 title="주 에이전트는 생성 응답을 먼저 받고 작업 종료 후 완료 알림을 받는다"
shape: sequence_diagram
lead: 주 에이전트
paseo: Paseo
worker: 하위 에이전트
lead -> paseo: "① list_profiles"
paseo -> lead: 설정·notes { style.stroke-dash: 3 }
lead -> paseo: "② create_agent\n설정·workspace·initialPrompt"
paseo -> worker: "③ 새 세션 시작"
paseo -> lead: "agentId·workspaceId\n작업 종료를 기다리지 않음" { style.stroke-dash: 3 }
worker.work: 구현·검증·보고
worker -> paseo: 종료·결과 { style.stroke-dash: 3 }
paseo -> lead: "④ 완료 알림" { style.stroke-dash: 3 }
lead -> paseo: "⑤ send_agent_prompt\nagentId로 후속 수정 요청"
paseo -> worker: 기존 세션에 전달
```

- **생성:** `create_agent`에 실행 설정·작업 위치·첫 작업 지시를 전달한다.
- **식별:** 반환된 `agentId`로 상태 조회·후속 지시를 보낸다. `workspaceId`는 작업 공간을 가리킨다.
- **완료 수신:** Paseo 에이전트에는 기본적으로 완료·오류·권한 요청 알림이 전달된다. `notifyOnFinish: false`로 끌 수 있다.
- **결과 판단:** 알림만으로 테스트 성공을 단정하지 않는다. 실제 보고·diff·검증 결과를 읽는다.
- **후속 지시:** `send_agent_prompt`는 기존 대화에 전달한다. 실행 중 지시는 기본적으로 steer이며, 지원하지 않으면 interrupt로 처리될 수 있다.
- **외부 MCP 클라이언트:** `get_agent_status`·`get_agent_activity`로 결과를 확인한다.

근거: [에이전트 도구](https://paseo.sh/docs/mcp.md#agents), [후속 지시](https://paseo.sh/docs/orchestration-workflows.md#send-a-prompt-to-another-agent).

## 프로필은 실행 설정이다

- **저장 항목:** provider·모델·모드·추론 수준·지원 기능 설정.
- **When to use:** 조율자가 프로필을 고를 때 읽는 `notes`. 실제 작업 지시는 `initialPrompt`로 따로 전달한다.
- **도구 사용:** `list_profiles`로 조회한 값을 `create_agent`의 인수로 옮긴다. `create_agent`에 프로필 이름을 넣는 전용 인수는 없다.
- **선택 실패:** 맞는 프로필이 없으면 `list_providers`·`list_models` 등으로 실제 가능한 설정을 확인한다.
- **변경 효과:** 저장한 프로필을 고쳐도 이미 실행 중인 에이전트 설정은 자동으로 바뀌지 않는다.

| 프로필 값 | 생성 요청에서 쓰는 자리 |
|---|---|
| provider + model | `provider/model` |
| modeId | `settings.modeId` |
| thinkingOptionId | `settings.thinkingOptionId` |
| featureValues | `settings.features` |
| notes | 주 에이전트의 선택 근거 |

근거: [프로필](https://paseo.sh/docs/agent-profiles.md), [생성 인수 매핑](https://paseo.sh/docs/mcp.md#agent-profiles).

## workspace와 부모 관계는 별개다

- **workspace:** 실제 작업 디렉터리와 에이전트·터미널 등을 묶는 공간.
- **부모 관계:** 어느 에이전트가 다른 에이전트에게 작업을 위임했는지 나타내는 관계.
- **기본 생성:** 에이전트가 `workspaceId` 없이 자식을 만들면 자기 workspace에 생성된다.
- **다른 위치:** 다른 `workspaceId`를 지정해도 자식이라는 관계는 유지된다.
- **코드 격리:** 별도 worktree가 필요하면 workspace를 먼저 만들고 그곳에 에이전트를 배치한다.

| 상황 | 작업 폴더 선택 |
|---|---|
| 구현 후 독립 리뷰 | 리뷰어가 구현자의 실제 폴더와 diff를 보게 한다 |
| 독립 변경을 병렬 구현 | 각각 별도 worktree를 사용하고 나중에 결과를 통합한다 |
| 같은 코드 조사 | 같은 workspace에서 읽기 작업을 나눌 수 있다 |

- 같은 폴더를 쓰는 새 대화는 **대화 맥락은 분리되지만 파일은 공유**한다.
- 다른 clone·worktree에는 미커밋 변경과 Git 제외 파일이 자동으로 따라가지 않는다.
- 이름이 같은 저장소인지보다 **실제 경로·브랜치·diff가 같은지** 확인한다.

근거: [workspace와 부모 관계](https://paseo.sh/docs/mcp.md#mental-model), [작업 분리 예](https://paseo.sh/docs/orchestration-workflows.md#parallelize-edits-without-collisions).

## 두 종류의 하위 에이전트

| 구분 | Paseo 하위 에이전트 | provider 내부 하위 에이전트 |
|---|---|---|
| 생성 | Paseo 도구·CLI | provider 자체 위임 도구 |
| provider 선택 | 호스트에 설정된 provider | 부모 provider의 시스템 안에서 결정 |
| 대화·제어 | 별도 세션, 후속 지시·설정 변경 가능 | 읽기 전용 타임라인, 수명은 provider가 관리 |
| 프로필 | 조율자가 설정을 읽어 적용 | Paseo 프로필이 자동 적용되지 않음 |

- **관찰:** Subagents track에서 위임된 작업을 확인한다.
- **일시 중단:** `cancel_agent`는 현재 실행을 중단하고 세션은 남긴다.
- **목록 정리:** `archive_agent`는 에이전트를 활성 목록에서 제외한다.
- **종료:** `kill_agent`는 세션을 종료한다.
- **부모에서 분리:** detach는 앱·CLI의 사용자 동작이며 MCP 도구로 제공하지 않는다.

근거: [작업 표시·제어](https://paseo.sh/docs/orchestration-workflows.md#where-the-work-appears), [도구 목록](https://paseo.sh/docs/mcp.md#agents).

## Superpowers와 조합한다

- **Superpowers:** 설계·계획·작업 배정·리뷰·ledger 절차. [자체 동작 설명](/coding-agents/superpowers-workflow/)을 따른다.
- **Paseo:** 그 절차에 필요한 구현자·리뷰어의 생성·설정·대화·작업 폴더 연결.
- **주 에이전트:** 스킬을 읽고 Paseo 도구를 호출한다. Paseo가 spec·plan을 해석해 자동 실행하는 것은 아니다.
- **폴더 구분:** Paseo workspace는 코드 작업 공간, `.superpowers/sdd/`는 그 코드 폴더 안의 임시 기록 공간이다.

<Steps>

1. **준비:** 도구를 켜고 프로필·실제 코드 폴더를 확인한다.
2. **입력:** 승인한 spec·plan을 주 에이전트에게 전달한다.
3. **실행:** SDD가 요구하는 구현자·리뷰어를 Paseo로 생성하고 brief·보고서·diff를 전달한다.
4. **확인:** 주 에이전트가 결과·리뷰·ledger를 관리하고 다음 작업으로 이어 간다.

</Steps>

```text title="승인한 계획을 Paseo로 실행하는 요청"
승인한 docs/superpowers/plans/2026-11-05-csv-export.md를 실행해 줘.
subagent-driven-development의 구현자·리뷰어 생성에는 Paseo 도구를 사용해 줘.
프로필과 When to use를 조회해 설정을 고르고, 구현자와 리뷰어가 같은 실제 코드 폴더를 보게 해 줘.
주 에이전트가 작업 배정·리뷰·ledger를 관리하고 기존 Git 정책을 따라 줘.
사용 불가능한 위임·리뷰 경로와 남은 문제를 알려 줘.
```

- 경로는 예시다. **이미 승인한 실제 계획 경로**로 바꿔 쓴다.
- SDD는 구현자를 동시에 여러 명 실행하지 않는다. Paseo가 병렬 실행을 지원해도 SDD의 절차는 유지한다.
- SDD의 작업 리뷰 위에 같은 diff의 별도 리뷰 흐름을 중복으로 붙이지 않는다.
- 직접 실행을 원하면 `executing-plans`로 구현하고 최종 독립 리뷰를 Paseo로 연결할 수 있다.
- 이 조합은 공식 기능을 연결한 운영 예다. **전체 결합 실행은 실측하지 않았다.**

## 결과에서 확인할 것

- **도구가 안 보인다:** 서버 실행 여부와 도구 주입 설정을 구별하고, 새 세션·reload 여부를 확인한다.
- **리뷰어가 변경을 못 본다:** 구현자와 리뷰어의 실제 경로·브랜치·diff를 대조한다.
- **프로필을 바꿨는데 모델이 그대로다:** 이미 실행 중인 세션에는 자동 반영되지 않는다.
- **완료 알림이 왔다:** 구현 보고·검증 명령과 결과·리뷰 지적 처리까지 확인한다.
