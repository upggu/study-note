## 제품 요구를 바꾼다

`docs/product-specs/PRD-task-manager.md`의 CSV 한도를 1,000건에서 5,000건으로 늘리는 예시다.
권한과 필터 정책은 유지하고, 5,001건부터는 제한 안내를 보여 주기로 결정했다고 가정한다.

```text
docs/product-specs/PRD-task-manager.md의 CSV 내보내기 한도를
1,000건에서 5,000건으로 늘리기로 했어. 조회 권한과 화면 필터 정책은 그대로야.
대상 5,000건은 다운로드 성공, 5,001건은 파일 대신 제한 안내가 기준이야.
create-prd로 기존 PRD에서 이 변경의 누락·영향을 검토하고,
합의한 변경을 같은 파일의 관련 설명에 반영해 줘.
새로 결정해야 할 제품 목적·범위·정책은 이유와 영향을 제안으로 남겨 줘.
superpowers로 변경 설계와 계획을 검토·승인받은 뒤 구현·문서 갱신·검증·최종 리뷰까지 진행해 줘.
커밋·푸시·PR 생성은 하지 마.
```

**받을 결과:** 기존 PRD의 변경 내역, 변경 설계·계획, 구현 diff와 경계값·권한·필터의 검증 결과다.
새 PRD 사본이나 요구 ID·상태 관리 양식을 추가하지 않는다.
제품 요구 변경을 검토한 사실이 개발 설계·계획의 승인을 대신하지 않는다.

아직 한도를 얼마나 늘릴지나 다른 해결 방향이 열려 있다면
[제품 기획과 PRD 리뷰 맡기기](/coding-agents/product-requirements/)에서 필요한 결정을 먼저 다룬다.
위처럼 변경을 이미 정했다면 제품 탐색을 처음부터 반복하지 않는다.
기술 검토에서 성능이나 사용 방식 때문에 제품 결정을 바꿔야 할 때는 그 영향만 다시 확인한다.

| 결과에서 확인할 것 | 변경 후 판정 기준 |
|---|---|
| 허용 범위 | 5,000건 전체의 CSV 다운로드가 성공한다. 1,000건에서 잘리거나 일부 페이지만 담기지 않는다 |
| 제한 경계 | 5,001건에서 CSV 대신 제한 안내를 보여 준다. 안내 문구에도 현재 한도가 반영된다 |
| 기존 정책 | 같은 조회 권한과 필터를 적용한다. 권한 없는 항목·필터 밖 항목이 섞이지 않는다 |
| 실제 검증 | 경계값과 정책 유지에 대해 무엇을 실행해 어떤 결과를 얻었는지 알 수 있다 |
| 문서와 제공 상태 | PRD와 기술 문서가 변경에 맞고, 구현한 것과 실제 출시한 것을 구분한다 |

## 문서는 구현과 함께 갱신한다

요구는 바뀌었는데 PRD에 1,000건이 남으면 다음 작업이 이전 한도를 기준으로 움직인다.
반대로 코드가 아직 이전 상태인데 “5,000건 제공”이라고 쓰면 사용할 수 있는 기능을 잘못 설명한다.
**결정한 변경과 구현·출시 여부를 기존 문서의 관련 설명에서 구분한다.**
예를 들어 구현 전에는 “CSV 한도를 5,000건으로 변경하기로 했다. 현재 제공 한도는 1,000건이다”라고 쓸 수 있다.
검증 뒤 출시를 하지 않았다면 “5,000건 구현·검증 완료, 출시 전”이라고 구분하고 출시 여부를 추정하지 않는다.

| 바뀐 사실 | 함께 고칠 곳 |
|---|---|
| 한도·제한 안내와 제품 동작 | 기존 PRD의 관련 요구·해결책·릴리스 설명 |
| 현재 API·구조·실행 방법·규약 | 해당 내용을 관리하는 기존 기술 문서나 README |
| 실행 중 결정·완료 작업·검증 결과 | 이번 작업의 ledger. 다음 작업에도 필요한 결정은 제품·기술 문서에도 반영 |

이 연결은 [프로젝트에 적용할 규칙](/coding-agents/project-setup/#ai가-적용할-연결-규칙)이다.
관련 구현과 문서를 함께 수정해 통합 검증과 최종 리뷰에서 대조한다.
최종 리뷰가 새 결정을 만들었다면 그 수정과 함께 지속 문서에도 반영하고 영향받는 검증·리뷰를 따른다.
문서 갱신을 최종 리뷰 뒤에 처음 시작하는 별도 정리 작업으로 미루지 않는다.

완료한 spec·plan은 당시 범위와 실행의 기록으로 보존한다.
후속 5,000건 변경을 반영하려고 완료한 1,000건 작업의 설계·계획을 최신 사양처럼 계속 고치지 않는다.
새 변경의 설계·계획은 현재 PRD·기술 문서와 기존 작업 기록을 읽고 만든다.
진행 중인 계획의 변경·기록 방식은 설치된 superpowers를 따른다.

## 같은 작업 폴더에서 재개한다

Codex에서 멈춘 작업을 Claude Code가 **동일한 로컬 폴더**에서 여는 경우다.
둘 중 하나만 계속 쓰거나 같은 도구의 새 세션으로 재개할 때도 같다.
다음은 진행 중인 최초 1,000건 작업의 계획을 이어 가는 요청이다.

```text
docs/superpowers/plans/2026-10-24-csv-export.md를 이어서 실행해 줘.
같은 작업 폴더의 지침·관련 PRD·spec·plan·ledger를 읽고
기존 승인·완료 기록을 git log·git status·git diff와 대조해 줘.
끝난 작업과 이미 승인한 범위를 반복하지 말고 남은 작업부터 진행해 줘.
현재 파일로 실행하지 않은 검증은 미확인으로 보고해 줘.
커밋·푸시·PR 생성은 하지 마.
```

**받을 결과:** 현재 코드와 기록이 맞는지 확인한 뒤 남은 작업을 실행한 결과다.
계획의 체크 표시나 ledger 한 줄만으로 구현 완료를 단정하지 않는다.
계획이 아직 승인 전이었다면 그 지점에서 검토를 이어 가며, 재개 요청을 승인 기록으로 꾸미지 않는다.

| 대조할 것 | 확인할 내용 |
|---|---|
| spec·plan·PRD | 같은 작업과 구현 범위를 가리키며 승인한 내용이 무엇인가 |
| ledger | 보통 `.superpowers/sdd/<계획 이름>/progress.md`에 있다. 첫 줄의 계획 경로와 완료·결정·검증 기록이 이번 작업의 것인가 |
| `git log` | ledger가 가리키는 커밋과 현재 기준이 맞는가 |
| `git status`·`git diff` | 미커밋·미추적 변경이 무엇이며 완료 기록 이후 코드가 달라졌는가. 스테이징된 변경도 따로 확인했는가 |
| 현재 검증 | 기록된 테스트가 어느 코드 상태의 결과인가. 현재 파일의 검증이 더 필요한가 |

superpowers 7.0.1의
[재개 기준](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/subagent-driven-development/references/resuming.md)은
해당 계획의 ledger로 완료 작업을 찾는다. 이 덱은 미커밋 변경까지 함께 대조하는 인계 조건을 더한다.
별도 수동 인계 양식을 만들 필요는 없다.

### ledger가 없을 때

원래 작업 폴더의 기록을 가져오지 않았는지 먼저 확인한다. 작업을 마치며 정상적으로 정리됐거나
아직 실행 전이라 기록이 없을 수도 있다. 없다는 사실만으로 계획을 처음부터 실행하지 않는다.
다음 문장을 재개 요청에 덧붙인다.

```text
ledger를 찾지 못하면 원래 작업 폴더의 기록을 가져올 수 있는지 먼저 확인해 줘.
구할 수 없으면 spec·plan·현재 코드·git log·status·diff·기존 검증 결과로 완료 범위를 복원해 줘.
확인한 완료 범위와 불확실한 부분을 구분하고, 필요한 검증 뒤 남은 작업부터 이어 가 줘.
```

**확인할 핵심:** 복원한 근거와 남은 불확실성이 드러나야 한다.
과거 테스트 결과만 있고 이후 코드가 바뀌었다면 현재 상태의 통과 증거로 쓰지 않는다.

## 다른 작업 폴더로 넘긴다

다른 clone·worktree·기기에서는 같은 계획 경로가 있어도 파일 상태가 다르다.
원래 폴더의 변경을 보존한 채 다음 항목을 맞춘 뒤 새 폴더에서 재개한다.

| 전달·확인할 것 | 빠지면 생기는 문제 |
|---|---|
| 기준 브랜치·커밋과 커밋된 변경 | 다른 코드 위에서 같은 작업을 반복하거나 잘못 수정한다 |
| 미커밋 변경과 스테이징된 변경 | 커밋만 받아서는 진행 중 구현을 이어받지 못한다 |
| 미추적 spec·plan·PRD·소스 등 필요한 파일 | `git diff`만 전달해도 새 파일은 빠질 수 있다 |
| Git에서 제외된 `.superpowers/sdd/<계획 이름>/`의 필요한 기록 | 같은 기기의 다른 폴더에도 ledger가 자동으로 생기지 않는다 |
| 필요한 로컬 실행 준비 | 런타임·의존성·환경 설정·테스트 데이터가 없어 기록과 같은 검증을 재현하지 못한다 |

비밀값을 인계 문서에 복사하지 않고 새 환경에서 필요한 설정을 준비한다.
원래 폴더를 지우거나 전체를 덮어쓰는 방식으로 상태를 맞추지 않는다.
실제 파일 전달과 준비를 마친 뒤 다음처럼 요청한다.

```text
이 폴더는 다른 작업 폴더에서 이어받은 곳이야.
기준은 [브랜치·커밋]이고 계획은 docs/superpowers/plans/2026-10-24-csv-export.md야.
전달한 미커밋·미추적 파일과 .superpowers/sdd/의 기록을 원래 작업 상태와 대조해 줘.
필요한 로컬 실행 준비도 확인하고, 빠진 파일이나 기록이 있으면 먼저 범위를 복원해 줘.
완료한 작업은 반복하지 말고 남은 작업부터 진행하며, 실행하지 못한 검증은 미확인으로 남겨 줘.
커밋·푸시·PR 생성은 하지 마.
```

**받을 결과:** 상태 일치·누락 파일·환경 준비의 확인과 이어서 수행한 작업의 결과다.
이 요청문은 파일을 자동으로 옮기지 않는다. 계획 경로를 건네는 것과 필요한 실제 파일을 전달하는 것을 구별한다.
새 세션에서 지침을 읽는지는 [준비 확인](/coding-agents/installation/#프로젝트-지침도-읽히는지-확인한다)으로 확인한다.
이 덱에서는 도구 간 독립 세션의 실제 이관·전체 실행을 시험하지 않았다. 위 내용은 인계 시 확인할 조건이다.

## 이해 확인

다른 clone에 계획 파일은 있는데 ledger가 없으면 처음부터 할까? 누락 기록을 찾고 코드·Git 상태·검증 근거로 완료 범위를 복원한다.
5,000건 테스트가 통과했으면 PRD에 출시 완료라고 써도 될까? 구현·검증과 실제 출시는 구분하고 확인한 상태만 쓴다.
