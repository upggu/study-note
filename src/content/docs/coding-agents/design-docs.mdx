- 새 작업은 관련 프로젝트 문서를 읽고 시작한다. 구조나 규약을 바꾸면 같은 작업에서 문서도 갱신한다.

## 작업별 설계와 프로젝트 설계의 차이

| 문서 | CSV 예시에서 담을 것 | 다음 변경이 생기면 |
|---|---|---|
| 작업별 spec | 업무 CSV를 추가하는 이유, 권한·필터·1,000건 제한과 완료 조건 | 새 작업의 spec에서 새 요구를 정한다. 끝난 spec은 당시 기록으로 남긴다 |
| 작업별 plan | API·화면·테스트를 구현할 순서와 파일 | 새 작업의 실행 계획을 만든다 |
| 프로젝트 설계·규약 | web → api → DB 흐름, CSV 생성 모듈, 조회 권한 적용 위치와 이유 | 바뀐 구조·규약을 현재 문서에 반영한다 |

작업 중 요구가 바뀌면 해당 spec과 plan을 맞춘다. 작업이 끝난 뒤 현재 구조를 알려 주기 위해 옛 spec을
계속 고치는 대신, 프로젝트 문서를 갱신한다.

## 현재 기준을 한 곳에서 찾는다

CSV 내보내기를 만들며 "제목이 `=`로 시작하면 앞에 작은따옴표를 붙인다"고 정했다. 이 결정은
`docs/superpowers/specs/2026-10-24-csv-export-design.md`의 접근법 절이나 ledger의 `Ruling:` 줄에 있다.
이 결정을 프로젝트 문서에 반영하지 않으면 다음 달 "댓글 CSV 내보내기"를 만드는 세션은 옛 파일부터
찾아 읽거나 다른 방식을 고른다. 현재 CSV 구조와 규약을 `csv-output.md`에 두면 그 문서를 참고해 새 spec을 만들 수 있다.

| 별도 문서로 나눌 신호 | 기존 문서를 유지할 수 있는 경우 |
|---|---|
| 현재 구조와 결정이 여러 작업 기록에 흩어져 있다 | README나 기존 구조 문서에서 현재 기준을 찾을 수 있다 |
| 여러 기능이 같은 데이터 흐름·규약을 공유한다 | 규모가 작아 기존 문서의 한 절로 충분하다 |

## 영역 하나에 파일 하나

현재 구조·책임·데이터 흐름을 설명하고 그렇게 정한 이유를 붙인다. 다음은 가상 CSV 기능의 프로젝트
문서다. 화면 목록과 CSV가 조회 권한은 공유하고 페이지 제한은 다르게 적용하는 이유까지 남긴다.

```md title="docs/design-docs/csv-output.md"
# CSV 구조와 출력 규약

CSV를 내려주는 모든 API에 적용한다. 첫 적용은 업무 목록 내보내기(docs/superpowers/specs/2026-10-24-csv-export-design.md).

## 구조와 데이터 흐름

- apps/web은 필터를 apps/api에 전달하고 반환된 CSV를 다운로드한다.
- apps/api가 사용자의 조회 권한과 필터를 적용해 DB에서 항목을 읽는다.
- 목록 API와 CSV API는 권한·필터 처리를 공유한다. 화면 페이지 제한은 목록 API에서만 적용한다.
- packages/csv는 조회된 항목을 CSV로 변환한다. DB 조회와 권한 판단은 맡지 않는다.

## 규약

- 생성은 packages/csv의 `toCsv()`만 쓴다. 직접 문자열을 이어 붙이지 않는다.
- 셀 값이 `=`·`+`·`-`·`@`로 시작하면 앞에 `'`를 붙인다.
- 건수 제한을 넘으면 파일 대신 413과 제한 안내를 반환한다.

## 결정

- 화면 목록 함수를 그대로 재사용하지 않은 이유: 페이지 제한이 함수 안에 있었다. 권한·필터 부분을 분리해 두 함수가 공유한다.
- 비동기 처리를 하지 않은 이유: 첫 요구가 1,000건 이하였다. 초과 요구가 생기면 이 문서를 고친다.
```

| 종류 | 답하는 질문 | 파일 예 |
|---|---|---|
| 구조 | 모듈이 어떻게 나뉘고 의존 방향은 무엇인가 | `architecture.md` |
| 데이터 | 스키마·마이그레이션·생성 파일을 어떻게 다루는가 | `database.md` |
| 규약 | 같은 종류의 문제를 어떻게 푸는가 | `csv-output.md`, `error-handling.md` |

타입·lint·테스트의 세부 규칙을 문서에 전부 복사하지 않는다. 문서는 구성 요소의 관계와 적용 범위,
결정 이유를 설명하고 세부 계약은 해당 코드·테스트로 연결한다.

## 언제 쓰고 어떻게 유지하는가

- **작업 시작:** AGENTS.md에 "CSV 출력을 만들거나 바꿀 때: docs/design-docs/csv-output.md"처럼 읽을 조건을 둔다. 관련 프로젝트 문서와 코드를 읽고 기존 구조·규약을 새 spec의 전제로 삼는다.
- **구현 중:** 구조·데이터 흐름·규약을 바꾸면 같은 작업에서 해당 프로젝트 문서도 갱신한다. spec·plan에는 이번 변경의 요구와 작업을, 프로젝트 문서에는 변경 후의 현재 기준을 적는다.
- **마무리:** 최종 리뷰에서 코드와 프로젝트 문서가 일치하는지 확인한다. ledger에만 남은 지속할 결정도 **리뷰와 ledger 삭제 전에** 반영한다. 실행 skill이 workspace를 지운 뒤 finishing으로 넘어간다([실행 순서](/coding-agents/design-and-plans/#ledger가-삭제되기-전에-결정을-옮긴다)).
- **결정 변경:** 본문의 현재 기준을 새 결정으로 갱신한다. 옛 이유가 필요하면 결정 기록에 "대체됨"으로 표시하고 새 이유를 적어 현재 규칙과 구별한다.
- 문서가 코드와 어긋난 것을 발견하면 그 자리에서 고친다. 별도 정리 작업을 기다리지 않는다.

## 이해 확인

새 기능이 CSV 생성 모듈의 위치를 바꿨다. 옛 작업의 spec만 고치면 될까? 현재 구조를 설명하는 프로젝트 문서와
관련 링크를 같은 작업에서 갱신한다. 새 spec·plan에는 이번 변경을 남기고, 완료된 옛 spec·plan은 당시 기록으로 보존한다.

댓글 CSV 내보내기를 만드는 세션이 수식 주입 방지 방법을 묻는다. 어디를 보게 할까? `docs/design-docs/csv-output.md`다.
AGENTS.md에 읽을 조건이 있으면 brainstorming이 묻기 전에 읽었을 것이다. 없다면 그 조건을 추가한다.

ledger의 `Ruling:` 줄을 전부 규약 문서로 옮겨야 할까? 아니다. 다음 기능에도 적용될 결정만 옮긴다.
"Task 2에서 조회 함수를 분리함"은 진행 정보라 ledger에 남기고, 분리한 결과와 이유만 옮긴다.
