<Thesis>

- 합의한 PRD는 개발의 입력이다. 제품 요구에 동의했어도 기술 접근법·설계 승인과 계획 리뷰·확인은 따로 거친다.
- 계획까지만 요청하면 구현 전에 멈춘다. 끝까지 맡겨도 필요한 설계·계획 승인을 건너뛰지 않는다.
- 결과는 요구한 동작·실제 검증·관련 문서의 일치를 대조한다. 실행하지 않은 검사는 미확인으로 남긴다.
- 기존 요구의 버그 수정에 제품 탐색이나 PRD 재작성을 반복하지 않는다. 제품 결정을 바꿔야 할 때 사용자에게 돌아간다.

</Thesis>

**합의한 제품 요구 → 개발 설계 승인 → 계획 리뷰·확인 → 구현·검증과 문서 갱신**으로 이어 간다.
이 페이지는 개발을 어디까지 맡기고 어떤 증거로 결과를 판단할지 안내한다.
[프로젝트에 적용하기](/coding-agents/project-setup/)에서 지침과 문서를 연결했고,
[제품 기획과 PRD 리뷰 맡기기](/coding-agents/product-requirements/)에서 요구를 합의했다고 가정한다.

## 개발 설계와 계획까지만 맡긴다

가상의 업무 서비스 task-manager에서 CSV 내보내기를 처음 구현하는 예시다.
PRD는 `docs/product-specs/PRD-task-manager.md`이며, 한도는 1,000건으로 합의했다고 가정한다.
자기 프로젝트의 실제 파일과 범위로 바꿔 요청한다.

```text
docs/product-specs/PRD-task-manager.md의 업무 목록 CSV 내보내기를 구현하려고 해.
조회 권한과 화면 필터를 적용한 전체 항목을 최대 1,000건 내보내고,
1,001건부터는 파일 대신 제한 안내를 보여 주는 범위야.
현재 지침·문서·코드를 읽고 superpowers로 접근법과 설계를 제안해 줘.
설계에 관련 PRD와 이번 범위를 연결하고 내 승인을 거쳐 구현·검증·문서 갱신 계획을 작성해 줘.
제품 목적·범위·정책을 바꿔야 하면 이유와 영향을 먼저 제안해 줘.
이번에는 계획 검토까지만 하고 구현은 시작하지 마.
```

**받을 결과:** 검토·승인을 거친 개발 설계와 실행 전 계획이다.
AI가 설명한 기술 접근법과 설계에 답한 뒤 계획을 받는다. 요청문 하나가 모든 승인을 대신하지 않는다.
예시의 설계·계획 파일은 각각 다음 경로다. 형식은 설치된 스킬이 정한다.

- 설계: `docs/superpowers/specs/2026-10-24-csv-export-design.md`
- 계획: `docs/superpowers/plans/2026-10-24-csv-export.md`

<Steps>

1. **입력과 범위를 확인한다.** AI가 실제 PRD·기술 문서·기존 코드를 읽었는지 본다.
   이번 구현 범위가 1,000건 한도와 기존 권한·필터 조건을 유지하는지 대조한다.
2. **접근법과 설계를 승인한다.** 구현 대안의 장단점과 선택 이유, 구조·제약·완료 조건을 확인한다.
   PRD에 동의한 사실만으로 이 승인이 끝난 것으로 취급하지 않는다.
3. **계획을 리뷰하고 실행 여부를 확인한다.** 설계를 구현할 작업과 검증, 관련 문서 갱신이 포함됐는지 본다.
   계획까지만 요청했다면 여기서 멈춘다. 실행 선호가 미리 정해져 있어도 계획 리뷰는 남는다.

</Steps>

이 순서는 확인한 Codex superpowers 7.0.1의
[brainstorming](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/brainstorming/SKILL.md)과
[writing-plans](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/writing-plans/SKILL.md#execution-handoff)에 따른다.
7.0.1은 작은 변경도 설계가 필요하면 짧은 설계 문서를 승인받는다.
확인한 Claude Code 7.0.0은 작은 변경의 설명을 대화에서 승인할 수 있다.
분명한 요청을 바로 실행하거나 질문을 생략하는 경우도 설치된 SKILL.md의 조건을 따른다.
이 덱이 별도로 파일 생략 기준이나 설계 양식을 만들지는 않는다.

## 승인 뒤 끝까지 실행하게 한다

계획을 읽고 이번 범위를 승인했다면 다음처럼 이어 간다.

```text
docs/superpowers/plans/2026-10-24-csv-export.md를 검토했고 이 범위로 실행해 줘.
프로젝트의 기존 Git·작업 폴더 정책과 사전 지정한 실행 선호를 따라 줘.
구현·관련 문서 갱신·검증·최종 리뷰까지 마치고 실제 결과와 남은 제한을 보고해 줘.
커밋·푸시·PR 생성은 하지 마.
```

**받을 결과:** 구현 diff, 실행한 검증과 결과, 갱신한 문서, 최종 리뷰와 남은 제한이다.
처음부터 실행까지 맡기려면 앞 요청의 마지막 문장을 “설계와 계획은 내 검토·승인을 거치고,
승인한 뒤에는 구현·문서 갱신·검증·최종 리뷰까지 진행해 줘”로 바꾼다.
새 승인이 필요한 설계·계획에서 멈추는 것과 이미 승인한 구현의 매 작업마다 계속할지 묻는 것은 구별한다.

예시의 사전 지정된 실행 선호는 subagent-driven-development이며 하위 에이전트 도구가 없으면 executing-plans다.
작업별 리뷰와 최종 리뷰는 설치된 실행 스킬을 따른다. 도구가 없어 native 실행에서 최종 self-review를 했다면
그 사실과 한계를 보고한다. 다른 코딩 도구의 추가 리뷰를 필수로 붙이지 않는다.
커밋·외부 반영은 이 요청과 실제 프로젝트 정책을 따르며 스킬의 기본 동작보다 사용자 지시가 우선한다.

## 결과를 요구와 대조한다

“완료했다”는 문장만으로 끝내지 않는다. 다음 표는 처음 합의한 1,000건 범위의 관찰 기준이다.
실제 제품을 구현한 결과가 아니라 개발 결과를 읽는 예시다.

| 확인할 것 | 받을 증거와 판정 기준 |
|---|---|
| 내보낼 대상 | 조회 권한과 화면 필터를 적용한 전체 결과가 CSV에 담긴다. 현재 화면의 한 페이지만 내보내지 않는다 |
| 한도 안의 동작 | 대상 1,000건에서 다운로드가 성공하고 CSV 내용·건수가 맞는다 |
| 한도 초과 동작 | 대상 1,001건에서 파일 대신 제한 안내를 보여 준다 |
| 권한과 필터 | 권한 없는 항목이 섞이지 않고, 필터 밖 항목도 내보내지 않는다 |
| 실제 검증 | 실행 명령·입력 조건·결과가 있다. 실행하지 못한 검사와 남은 문제는 구분한다 |
| 문서와 리뷰 | PRD의 관련 설명·현재 기술 문서가 구현과 맞고 최종 리뷰 범위에 포함됐다. 리뷰에서 생긴 결정도 해당 수정과 함께 반영됐다 |

관련 문서 갱신은 [프로젝트의 연결 규칙](/coding-agents/project-setup/#ai가-적용할-연결-규칙)으로 더한 것이다.
구현과 함께 반영해 통합 검증·최종 리뷰에서 코드와 대조한다. 제품 성과나 출시를 실제로 확인하지 않았다면
테스트 통과를 사용자 문제 해결·출시 완료로 보고하지 않는다.
완료한 설계·계획은 당시 기록으로 보존하고 다음 작업의 현재 기준으로 계속 고치지 않는다.

## 기존 요구의 버그를 고친다

이미 합의한 요구와 실제 동작이 어긋난 경우에는 재현 조건과 기대 결과를 준다.

```text
docs/product-specs/PRD-task-manager.md의 CSV 내보내기를 확인해 줘.
필터 결과가 800건인데 현재 화면의 20건만 내보내져.
기존 요구는 권한과 필터를 적용한 전체 결과, 최대 1,000건이야.
원인을 재현해 수정하고 검증해 줘. 제품 목적·범위·정책은 바꾸지 마.
```

**받을 결과:** 재현한 원인, 수정 diff, 800건 전체와 기존 한도·권한·필터를 확인한 검증 결과다.
이 요청은 제품 방향 탐색이나 PRD 재작성이 필요하지 않다. superpowers가 적용하는 진단·개발 절차는 따른다.
고치려면 한도나 권한 정책 자체를 바꿔야 하는 경우에만 이유와 영향을 제안하고 제품 결정을 확인한다.
필요한 탐색·PRD 검토는 [제품 기획](/coding-agents/product-requirements/)으로,
합의한 요구의 실제 변경은 [변경 요청](/coding-agents/updates-and-handoff/#제품-요구를-바꾼다)으로 연결한다.

## 이해 확인

PRD에 동의했으니 설계와 계획을 보지 않고 구현해도 될까? 제품 결정은 개발의 입력이며 기술 설계·계획의 승인은 따로 필요하다.
계획까지만 맡겼는데 코드가 없으면 미완료일까? 검토할 설계·계획을 받았고 구현 전에 멈췄다면 요청 범위를 지킨 것이다.
