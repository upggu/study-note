- 관련 프로젝트 문서와 코드를 읽고 작업별 spec·plan을 만든다. 구현·검증 뒤 바뀐 현재 구조·규약을 같은 작업에서 갱신한다.
- 요청문에는 얻을 결과와 멈출 지점을 적는다. AGENTS.md가 읽을 문서와 작업 방식을 연결한다.
- 사람이 결정하는 지점은 셋이다. 설계 승인, 계획 승인과 실행 방식, 끝난 뒤 merge·PR 선택.
- 도구를 바꿀 때 코드의 커밋·남은 미커밋 변경과 ledger를 함께 넘긴다. 재개는 계획 경로 하나로 한다.

</Thesis>

**프로젝트 문서 참고 → 작업별 spec → plan → 구현·검증 → 프로젝트 문서 갱신**이 한 작업의 흐름이다.
갱신한 문서를 다음 작업이 다시 참고한다. 이 페이지는 **이 흐름에서 무엇을 확인하고, 다른 도구로 어떻게
이어받는가**에 답한다. 가상 CSV 내보내기를 Codex로 시작해 Claude Code로 넘기는 예다.

## 한 작업의 순서

다음은 설계·계획 파일을 만드는 작업의 흐름이다. 작은 수정은
[AGENTS.md에 정한 파일 생략 원칙](/coding-agents/design-and-plans/#세-파일이-생기는-순서)을 따른다.

<Steps>

1. **현재 기준을 읽고 요청을 구체화한다.** "업무 목록 CSV 내보내기를 만들어 줘"라고 요청하면,
   AGENTS.md가 연결한 관련 프로젝트 문서와 코드를 읽는다. 기존 API·권한 처리·CSV 구조를 새 작업의 전제로 삼는다.

2. **작업별 설계(spec)를 승인한다.** brainstorming에서 이번에 바꿀 동작·제외 범위·완료 조건을 정한다.
   `docs/superpowers/specs/`에 설계를 남긴다. 기존 규약을 바꿔야 한다면 이유와 영향을 설계에 드러낸다.

3. **계획(plan)을 승인하고 실행 방식을 고른다.** writing-plans가 spec을 구현·검증할 작업을
   `docs/superpowers/plans/`에 쓰고 subagent-driven과 native 중 하나를 추천한다. 구조·규약을 바꾸는 작업에는 관련 프로젝트 문서 갱신도 포함한다.
   실행을 시작할 때 using-git-worktrees로 별도 브랜치의 작업 공간을 준비하거나 기존 공간을 확인한다.

4. <span id="결과는-세-종류의-증거로-읽는다" />
   **구현·검증하고 프로젝트 문서를 갱신한다.** 계획을 실행하며 ledger에 진행 상황을 남기고, spec의
   입력·예상 결과와 실제 검증을 대조한다. 변경 후의 구조·규약은 [프로젝트 설계·규약 문서](/coding-agents/design-docs/)에
   반영한다. 계획의 작업 단위로 검증한 변경을 커밋하고, ledger에 커밋 범위와 결과를 남긴다.
   최종 리뷰와 ledger 삭제 전에 문서와 코드의 일치를 확인한다.

5. **작업을 마친다.** 최종 리뷰 뒤 workspace가 삭제되고, finishing-a-development-branch가 테스트를 확인한 뒤
   merge·PR·보류 등을 묻는다. 완료된 spec·plan은 당시 기록으로 남기고, 다음 작업은 갱신된 프로젝트 문서에서 시작한다.

</Steps>

superpowers README의 [The Basic Workflow](https://github.com/obra/superpowers#the-basic-workflow)가
기본 절차의 정본이다. 이 덱은 구현 변경과 함께 프로젝트 문서를 갱신하는 원칙을 더한다. 주요 승인·선택 지점은 2·3·5다.

## 요청문은 결과와 멈출 지점만

```text
업무 목록 CSV 내보내기를 만들어 줘. 권한과 화면 필터를 그대로 적용한 전체 항목, 최대 1,000건.
계획까지 만들고 실행 전에 멈춰 줘.
```

둘째 줄이 멈출 지점이다. 끝까지 맡기면 "계획을 승인하면 끝까지 실행하고 PR은 만들지 마"로 바꾼다.
커밋은 superpowers의 구현 절차에 포함된다. 리뷰는 작업별·브랜치 전체의 커밋 범위를 기준으로 하고,
마지막 merge·push·PR·브랜치 보존은 finishing 단계에서 고른다
([실행 절차](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/executing-plans/SKILL.md),
[마무리 선택](https://github.com/obra/superpowers/blob/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills/finishing-a-development-branch/SKILL.md)).

## 도구를 바꾸기 전에 챙길 것

Codex에서 Task 2까지 끝내고 Claude Code로 넘긴다. 별도 인계 문서는 쓰지 않는다. superpowers가
ledger에 완료 작업·결정·테스트 결과를 이미 적었다. 먼저 다음 도구가 **같은 작업 폴더**를 여는지 확인한다.

| 확인 | 왜 |
|---|---|
| 같은 코드 상태인가 | `git log`로 기준 커밋을, `git status`·`git diff`로 미커밋 변경을 대조한다. 커밋하지 않은 변경도 같은 작업 폴더에서는 이어받을 수 있다. 다른 clone·worktree라면 함께 옮긴다 |
| `.superpowers/sdd/<계획 이름>/progress.md`가 다음 도구에서 보이는가 | 같은 작업 폴더면 보인다. 다른 clone·worktree라면 같은 기기여도 [별도로 전달](/coding-agents/design-and-plans/#다른-작업-폴더로-넘길-때)하고, ledger가 가리키는 계획과 코드 상태가 맞는지 확인한다 |

<span id="새-세션은-파일에서-재개한다" />

## 재개는 계획 경로 하나로

새 도구에 줄 요청이다. 실행 skill이 ledger를 읽고 끝난 작업을 건너뛴다.

```text
docs/superpowers/plans/2026-10-24-csv-export.md를 이어서 실행해 줘.
ledger와 git log·git status·git diff를 대조해 끝난 작업은 반복하지 말고, PR은 만들지 마.
```

ledger가 없는 작업 폴더라면 원래 폴더에서 ledger와 미커밋 변경을 가져왔는지 먼저 확인한다. 기록을 구할 수 없으면
"ledger가 없으니 계획과 실제 코드·git log·git diff·검증 결과를 대조해 어디까지 됐는지 확인하고 이어 가 줘"를
덧붙인다. 계획에 체크된 단계가 있어도 그 뒤 코드가 바뀌었으면 테스트 결과는 현재 상태를 증명하지 않는다.

## 두 도구를 나눠 쓰는 배치

한쪽이 구현하고 다른 쪽이 리뷰하는 배치가 자연스럽다. superpowers의 subagent-driven은 같은 도구 안에서
새 컨텍스트로 리뷰하지만, 도구를 바꾸면 모델까지 바뀐다. Claude Code 공식 안내도 완료로 치기 전에
별도 컨텍스트의 리뷰를 권한다([Add an adversarial review step](https://code.claude.com/docs/en/best-practices#add-an-adversarial-review-step)).

```text
docs/superpowers/plans/2026-10-24-csv-export.md와 해당 spec을 현재 브랜치의 diff와 대조해 줘.
설계의 요구마다 구현·테스트가 있는지, 계획 밖 변경이 섞였는지, ledger의 Ruling이 타당한지 확인해 줘.
바뀐 구조·규약이 관련 프로젝트 문서에 반영됐고 현재 코드와 일치하는지도 확인해 줘.
정확성과 요구 누락만 보고하고 수정은 하지 마.
```

리뷰어는 결함을 찾으라는 요청을 받았으므로 무언가는 보고한다. 요구나 정확성에 닿는 지적만 반영한다.

## 이해 확인

Claude Code에서 계획을 열었는데 ledger는 Task 2 완료인데 그 커밋이 없다. Task 3으로 갈까? 안 간다.
다른 브랜치·worktree에 있는지, 다른 기기에서 푸시가 안 됐는지 확인해 상태부터 맞춘다.

작은 오타 수정을 요청했는데 brainstorming이 질문을 시작했다. 정상일까? v7.0.1부터 brainstorming은
분명한 요청은 바로 하고, 자동으로 시작했을 때는 "그냥 진행할까요"를 함께 묻는다. 진행하라고 답하면 된다.
