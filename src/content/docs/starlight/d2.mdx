## 관계를 알아야 하면 다이어그램을 쓴다

이 사이트는 **D2**라는 도구로 구성 요소와 연결을 그림으로 만든다.
AI가 텍스트로 원본을 작성하므로 나중에 관계나 이름을 바꾸기 쉽다.
[D2 공식 소개](https://d2lang.com/tour/intro/)에서 원본과 그림의 대응을 볼 수 있다.

다음은 이 사이트에서 문서가 발전하는 과정을 단순화한 그림이다.
**검증을 마친 초안도 사람이 읽은 뒤 다시 수정될 수 있다**는 점을 본다.

```d2 title="AI가 작성하고 검증한 문서를 사람이 읽고 피드백하면 AI의 수정으로 돌아오는 흐름"
direction: down
classes: {
  key: { style: { fill: "#dbeafe"; stroke: "#2563eb"; font-color: "#1e3a8a" } }
  mute: { style: { fill: "#f1f5f9"; stroke: "#94a3b8"; font-color: "#334155" } }
  ok: { style: { fill: "#dcfce7"; stroke: "#16a34a"; font-color: "#14532d" } }
}
ai: "AI\n자료 확인 · 작성 · 수정" { class: key }
review: "AI\n의미 리뷰 · 기술 검증" { class: mute }
reader: "사람\n화면을 읽고 예제 확인" { class: key }
published: "웹 문서\n검색 · 참조 · 공유" { class: ok }
ai -> review
review -> reader: 결과 전달
reader -> ai: 막힌 지점 피드백
reader -> published: 공유할 결과 확정 · 배포 요청
```

아래로 내려가는 선은 작성한 결과가 독자와 공유 대상으로 이어지는 흐름이다.
위로 돌아가는 선은 읽다가 생긴 의문을 다음 수정에 반영하는 흐름이다.
AI의 검증 통과와 사람의 이해는 서로 다른 확인 단계다.

## 텍스트가 그림이 되는 과정

위 그림의 화살표 하나는 다음처럼 적을 수 있다. **전체 그림 중 한 연결을 발췌한 예**다.

```text
review: AI 의미 리뷰 · 기술 검증
reader: 사람 화면 확인
review -> reader: 결과 전달
```

`review`와 `reader`는 요소를 구별하는 이름이고, 콜론 뒤는 화면에 보일 말이다.
`->`가 방향을, 뒤의 `결과 전달`이 화살표의 뜻을 정한다. AI는 이 텍스트를 MDX 본문의
`d2` 코드 블록에 넣는다. 관계가 바뀌면 이미지 편집기 대신 원본 텍스트를 수정하고 다시 빌드한다.

<span id="내장-컴포넌트와-다른-점" />

D2는 Starlight의 내장 컴포넌트가 아니다. 이 사이트에서는 다음 도구들이 역할을 나눈다.

| 단계 | 맡는 도구 | 독자에게 보이는 결과 |
|---|---|---|
| 원본 작성 | D2 문법 | 요소·경계·화살표를 텍스트로 기록 |
| 사이트 빌드 | 저장소의 D2 통합과 D2 실행 파일 | 코드 블록을 SVG 이미지로 변환 |
| 페이지 열기 | 브라우저의 이미지 표시 | 완성된 그림을 바로 표시 |
| 그림 확대 버튼 | 이 사이트의 D2 전용 UI | 확대 dialog에서 자세히 읽고 닫기 |

D2 통합은 이 저장소가 직접 가진 작은 Astro 통합이다. 저장소 설정은 이를 `starlight()`보다
먼저 등록하고, 고정된 버전의 [D2](https://d2lang.com/) 실행 파일로 기본적으로 외부 SVG 이미지를 만든다.
그림을 그리는 D2 엔진은 브라우저에서 실행하지 않지만, 확대·설명·재생 조작에는 별도 스크립트를 사용한다.
모든 D2 그림에 같은 전용 UI가 자동으로 붙는다. 일반 사진·스크린샷의 확대는 starlight-image-zoom이 맡는다.

## Mermaid에서 D2로 — 왜 갈아탔나

이 저장소는 예전에 Mermaid로 다이어그램을 작성했다. 당시 통합은 페이지를 연 브라우저에서
그림을 만들었기 때문에, 사이트 빌드가 끝나도 그림의 문법 오류가 뒤늦게 드러날 수 있었다.
AI가 여러 페이지를 고치는 작업에서는 **배포 전에 오류를 발견하고 완성된 이미지를 확인하는 흐름**이 필요했다.
2026년 8월에 기존 그림을 D2로 옮기고 Mermaid 통합을 제거했다.

| 판단 기준 | 이 사이트의 이전 Mermaid 통합 | 현재 D2 통합 |
|---|---|---|
| 그림을 만드는 시점 | 페이지를 여는 브라우저에서 렌더 | 사이트 빌드 때 SVG 생성 |
| 문법 오류 확인 | 빌드 외에 브라우저 렌더 확인 필요 | D2 변환 실패가 빌드 오류로 드러남 |
| 확대 방식 | 이전 다이어그램용 표시·확대 처리 | 모든 D2에 같은 전용 확대 UI 자동 적용 |
| AI의 수정 결과 확인 | 브라우저에 그려진 결과를 확인 | 생성한 SVG·PNG를 빌드·브라우저와 별도로 검사 가능 |

이 비교는 **이 저장소에서 사용한 통합 방식**의 비교다.
[Mermaid CLI](https://github.com/mermaid-js/mermaid-cli)도 SVG·PNG·PDF를 미리 생성할 수 있으므로,
“Mermaid는 빌드 때 검사할 수 없다”거나 “D2만 정적 그림을 만들 수 있다”는 뜻은 아니다.
두 도구 모두 텍스트 원본을 Git에서 관리할 수 있다.

이 사이트는 D2로 전환하면서 빌드 검증·이미지 확대·색과 배치 규칙을 한 방식으로 정리했다.
현재는 D2 실행 파일의 버전도 고정해 로컬과 배포 환경이 같은 도구로 그리게 한다.
이미 Mermaid의 문법과 사전 렌더가 잘 갖춰진 다른 문서라면 그 방식을 유지할 수도 있다.
D2가 더 빠르거나 AI가 더 정확하게 작성한다고 실측한 것은 아니다.

## 자동 배치에도 확인할 부분이 있다

D2를 골랐다고 그림이 저절로 읽기 좋아지는 것은 아니다. 이 사이트의 기본 배치 엔진은
[ELK](https://d2lang.com/tour/layouts/)이고, 넓은 그림은 본문에 맞춰 축소되어 글자가 작아질 수 있다.
세로로 배치하거나 질문별로 그림을 나누고, 필요할 때 눌러 확대해서 읽는다.

색은 성공·실패·주의·핵심 대상처럼 사이트에서 정한 의미로 사용하고, 라벨에도 뜻을 적는다.
노드에서 관련 페이지로 이동하거나 설명을 읽고, 탭을 골라 서로 다른 단계를 비교할 수 있다.
아래에서 링크·설명과 단계 선택을 직접 사용해 본다. 그림의 화살표는 설명용이며 실제 요청을 보내지는 않는다.

## 노드에 링크와 짧은 설명을 달 수 있다

D2 그림에는 공통으로 **그림 확대** 버튼이 있다. 그림 안에 링크나 설명을 넣으면
사이트가 자동으로 노드 조작이 가능한 방식으로 표시한다.
독자에게 보이는 차이는 다음과 같다. 아래 그림에서 직접 확인한다.

- **노드에 마우스를 올리거나 키보드로 초점을 옮기면** 아래 설명 영역에 짧은 설명이 나타난다. 터치 화면에서는 ⓘ를 누른다.
- **링크가 있는 노드나 체인 아이콘을 누르면** 연결된 페이지로 이동한다.
- **그림 확대** 버튼은 그림만 크게 보여 준다. 확대 화면에서도 링크·설명이 동작하며, Escape로 닫을 수 있다.

```d2 sketch=false title="관계·실제 화면·단계별 상태에 맞는 안내를 고르는 기준. 노드를 누르면 해당 안내 페이지로 이동한다."
direction: down
classes: {
  key: { style: { fill: "#dbeafe"; stroke: "#2563eb"; font-color: "#1e3a8a" } }
  mute: { style: { fill: "#f1f5f9"; stroke: "#94a3b8"; font-color: "#334155" } }
}
diagram: "D2 다이어그램\n(이 페이지)" {
  class: key
  tooltip: 요소의 관계·경계·방향을 보여 준다. 아래 예제에서는 단계도 선택할 수 있다
}
picture: "이미지 안내" {
  class: mute
  link: /starlight/components/
  tooltip: 제품 화면의 실제 위치와 모양을 보여 줄 때 쓴다
}
flow: "단계별 상태 예제" {
  class: mute
  link: "/starlight/d2/#단계를-골라-요청과-응답을-비교한다"
  tooltip: 요청 도착과 응답 도착의 전달 값과 보관 상태를 비교한다
}
diagram -> picture: 실제 화면 모양이 궁금하면
diagram -> flow: 단계별 상태가 궁금하면
```

그림의 **이미지 안내**는 [실제 화면을 보여 주는 방법](/starlight/components/)으로,
**단계별 상태 예제**는 [아래 요청·응답 비교](#단계를-골라-요청과-응답을-비교한다)로 연결된다.
D2는 관계를, 이미지는 실제 모양을 보여 준다. 단계별 상태는 아래처럼 D2로도 비교할 수 있다.
설명과 링크를 본문에도 두면 터치 화면이나 검색으로도 같은 내용을 찾을 수 있다. 요청은 결과로 말하면 된다.

```text
이 구성도의 각 컴포넌트 노드를 누르면 해당 컴포넌트 페이지로 가게 해줘.
노드에 마우스를 올리면 한 줄 설명이 보이게 하고, 설명은 본문에도 남겨줘.
```

## 단계를 골라 요청과 응답을 비교한다

아래는 브라우저와 서버의 요청·응답을 **D2 그림과 단계 탭으로 표현한 예제**다.
고정된 두 상자와 왕복 화살표에서 현재 전달 방향을 강조한다.
먼저 **요청 도착**과 **응답 도착**을 번갈아 고르고, 원하면 **흐름 재생**으로 방향을 따라간다.
흐르는 선은 전달 방향을 강조할 뿐, 실제 속도나 반복 요청을 뜻하지 않는다.
**그림 확대**를 누른 뒤에도 같은 단계 선택과 재생·정지 버튼을 사용할 수 있다.
확대 화면에서 요청 도착을 재생한 뒤 응답 도착을 골라, 강조된 화살표의 방향과 아래 상태 설명이
함께 바뀌는지 확인한다. 직접 조절한 배율은 유지되며, 닫으면 마지막으로 본 단계가 본문에도 선택된다.

<Tabs>
<TabItem label="요청 도착">

```d2 sketch=false target=root title="브라우저가 GET /guide를 보내고 서버가 요청을 받은 시점"
...@request-response
```

서버가 `GET /guide` 요청을 받았다. **브라우저에는 아직 문서가 없다.** 연한 응답 화살표는 이후 경로다.

</TabItem>
<TabItem label="응답 도착">

```d2 sketch=false target=steps.response title="서버의 HTML 응답이 브라우저에 도착하고 서버의 원본은 유지되는 시점"
...@request-response
```

서버가 보낸 **HTML 문서가 브라우저에도 도착했다.** HTML은 브라우저가 페이지를 구성할 때 읽는 문서 형식이다.
서버의 원본 문서는 그대로 남는다. 연한 요청 화살표는 이미 지나온 경로다.

</TabItem>
</Tabs>

단계는 자동으로 넘어가지 않는다. 재생을 정지해도 화살표와 상태 설명으로 같은 내용을 읽을 수 있다.
기기의 **동작 줄이기** 설정이 켜져 있으면 정지 그림을 보여 준다.
아래 표는 탭 밖에서도 두 시점의 보관 상태를 비교할 수 있게 남긴 것이다.

| 단계가 끝난 시점 | 브라우저 | 서버 |
|---|---|---|
| 요청 도착 | 요청 주소를 알고 응답 대기. 문서 없음 | 요청 경로와 원본 문서 보유 |
| 응답 도착 | 응답 문서 수신. 페이지 구성에 사용 가능 | 원본 문서 유지 |

캐시·실패·연결 설정을 생략한 설명용 사례다. **요청이 도착한 순간과 문서가 도착한 순간은 다르다**는 차이를 본다.
이처럼 몇 단계의 관계와 상태는 D2 단계 탭과 상태 표로 비교할 수 있다.
단계가 많아지면 흐름을 나누고, 전체 순서는 단계 목록으로 함께 보여 준다.
입력값에 따라 결과를 계산하는 예제는 별도 인터랙티브 데모가 필요하다.

[D2의 steps](https://d2lang.com/tour/steps/)는 이전 단계의 그림을 이어받는다.
이 사이트의 탭과 재생·정지 버튼은 그 그림을 읽기 쉽게 붙인 화면 기능이며, D2가 상태를 계산하는 것은 아니다.

## AI에게 그림을 요청한다

그림의 모양보다 **관계와 질문**을 먼저 준다.

```text
이 페이지의 로그인 설명을 D2 다이어그램으로 보완해줘.
브라우저·앱 서버·인증 서버의 경계를 구분하고,
누가 요청하고 어떤 값을 응답하는지 화살표에 적어줘.
그림 아래에는 읽을 순서와 이번 예제에서 생략한 조건을 설명해줘.
본문 폭에서 글자가 잘 읽히도록 배치하고 렌더 결과를 확인해줘.
```

그림 하나에 모든 예외를 넣을 필요는 없다. 정상 흐름을 먼저 읽게 하고,
실패 경로가 별도 질문이라면 그림이나 절을 나눠 달라고 요청한다.

## 그림을 보고 피드백한다

| 확인할 것 | 피드백 예 |
|---|---|
| 화살표 방향과 의미 | 이 화살표가 요청인지 응답인지 모르겠어. 보내는 값과 방향을 분명히 해줘 |
| 구성 요소의 경계 | 브라우저와 서버 내부 데이터가 섞여 보여. 어디에 보관되는지 구분해줘 |
| 읽는 순서 | 어디부터 따라가야 할지 모르겠어. 출발점과 관찰할 순서를 설명해줘 |
| 글자와 배치 | 확대해야만 라벨이 읽혀. 그림을 나누거나 세로로 배치해줘 |
| 본문과 일치 | 본문은 검증 후 저장한다고 하는데 그림에는 검증이 없어. 근거와 대조해 맞춰줘 |

D2는 **그림 확대** 버튼으로, 일반 본문 이미지는 이미지를 눌러 확대한다.
확대가 가능해도 기본 화면에서 핵심 관계는 읽혀야 한다.
색만으로 성공·실패를 구별하지 말고 라벨에도 의미가 드러나게 한다.

## 이해 확인

**그림의 빌드가 성공했는데 요청 화살표가 거꾸로라면 검증이 끝난 것일까?**
문법은 유효하지만 설명은 틀릴 수 있다. 본문의 요청 주체·수신자와 화살표를 대조해야 한다.
글자가 겹치거나 지나치게 작다면 배치를 바꾸고 렌더 결과를 다시 확인한다.

## 단계마다 남는 값이 궁금하면

전체 관계가 보여도 “지금 이 순간 브라우저가 무엇을 갖고 있는가?”는 한 장의 그림으로 따라가기 어려울 수 있다.
위의 단계 탭처럼 **그림과 각 시점의 상태를 함께** 보여 달라고 요청한다.
단계가 끝난 시점의 상태를 표로 남기면 여러 시점을 한눈에 비교할 수 있다.

D2 문법·색·배치·상호작용과 검증은 AI가 D2 작성 지침(`docs/d2-authoring.md`)을
따라 처리한다. 사람은 그림이 자신의 질문에 답하는지를 보고 피드백하면 된다.
