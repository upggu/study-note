<Thesis>

- Cloudflare Pages에 Git 저장소를 연결하면 main 푸시 후 자동 배포하도록 구성할 수 있다.
- 빌드 명령은 `npm run build`, 출력 폴더는 `dist`다. Node 버전과 D2 준비는 저장소 파일에서 관리한다.
- 배포 성공 뒤에는 대표 주소·본문·검색·수정일을 확인한다. 실제 운영 값은 배포 운영 문서가 정본이다.
- 본인만 보려면 운영·미리보기·연결한 도메인 모두에 Cloudflare Access를 적용한다. PIN 인증은 유효한 로그인 세션 동안 반복하지 않는다.

</Thesis>

이 페이지는 **대시보드에서 무엇을 넣고, 저장소가 이미 무엇을 대신 처리하는가**에 답한다.

호스팅 계정·프로젝트·도메인은 자신의 값으로 설정한다.

## 대시보드에서 연결한다

[Pages의 Git 연동](https://developers.cloudflare.com/pages/get-started/git-integration/)으로
GitHub 저장소를 연결한다. 이미 연결했다면 아래 설정 표부터 확인한다.

<Steps>

1. Cloudflare 대시보드의 **Workers & Pages → Create Application**을 누른다.

2. **Create an app** 화면에서는 Workers 생성 안내가 먼저 보인다.
   **화면 맨 아래에 작게 표시된 Continue to Pages**를 눌러 Pages 생성 화면으로 이동한다.

3. Pages 화면에서 **Connect to Git**으로 GitHub에 로그인하고 저장소 접근을 승인한다.
   배포할 저장소를 고른 뒤 **Begin setup**을 누른다.

4. 다음 표대로 설정한다. `package.json`이 저장소 루트에 있는 이 프로젝트 기준이다.

   | 항목 | 입력하거나 선택할 값 |
   |---|---|
   | Project name | 원하는 프로젝트 이름. 기본 주소의 `<프로젝트>.pages.dev` 부분에 사용된다 |
   | Production branch | `main` |
   | Framework preset | `None`으로 둔다 |
   | Build command | `npm run build` |
   | Build output directory | `dist` |
   | Root directory (advanced) | 비워 둔다 — 저장소 루트 사용 |
   | Environment variables | 추가하지 않는다 — 기본 빌드에 별도 입력 불필요 |

   프리셋은 빌드 명령과 출력 폴더를 미리 채워 주는 기능이다. `None`이어도 위 두 값을 직접
   입력하면 된다. `npm run build`는 Git 이력을 준비하는 과정도 함께 실행하므로 그대로 입력한다.

5. **Save and Deploy**를 누른다. 끝나면 `<프로젝트>.pages.dev` 주소가 생기고, `main` 푸시는 프로덕션,
   다른 브랜치는 Preview 대상 설정에 따라 미리보기로 배포된다.

</Steps>

## 버전은 저장소 파일이 정한다

[Cloudflare 빌드 이미지 문서](https://developers.cloudflare.com/pages/configuration/build-image/)에
따르면 v3 이미지는 Node와 패키지 관리자 버전을 `package.json`의 `engines`에서 읽지 않는다. 대신 Node는
`.nvmrc`를 읽고, 저장소에 `24`가 들어 있다. npm은 그 Node에 딸려 오므로 따로 정할 것이 없다.
`package-lock.json`은 npm 의존성 버전의 기준이며, 설치 결과는 첫 빌드 로그에서 확인한다.

## 저장소가 대신 처리하는 것

빌드 명령을 실행하면 최근 수정일에 필요한 Git 이력과 다이어그램을 만드는 D2를 저장소가 준비한다.

| 스크립트 | 언제 | 하는 일 |
|---|---|---|
| `scripts/prepare-git-history.mjs` | `npm run build`의 `prebuild` | Pages에서 받은 Git 이력이 일부뿐이면 전체 이력을 가져온다. 랜딩의 "마지막 수정"을 정확하게 표시하는 데 필요하다 |
| `scripts/prepare-d2.mjs` | `astro.config.mjs` 로드 시 | 고정 버전 D2 바이너리를 `node_modules/.astro/d2/`에 내려받고 검증한다. build cache가 켜져 있으면 다음 빌드에서 다운로드를 건너뛴다 |

최근 수정일을 위한 이력 준비는 Pages가 [자동으로 제공하는 환경 변수](https://developers.cloudflare.com/pages/configuration/build-configuration/#environment-variables)
`CF_PAGES=1`을 보고 실행된다. **직접 환경 변수에 추가할 필요는 없다.**
D2 설치 명령도 따로 넣지 않는다. 전체 Git 이력을 가져오는 데 실패하면 잘못된 수정일을 내보내지 않도록 빌드도 실패한다.

## 주소와 site를 맞춘다

**Custom domains** 탭에서 도메인을 붙이면 `pages.dev` 기본 주소와 둘 다 살아 있다.
`src/config/site.mjs`의 `site`를 대표 주소로 두면 두 주소 모두 canonical이 그쪽을 가리켜
대표 URL을 알린다. canonical은 HTTP 리다이렉트나 검색엔진의 색인 결과를 보장하는 설정은 아니다.

```bash
curl -s 'https://YOUR-DOMAIN.example/' | grep -o '<link rel="canonical"[^>]*>'
curl -s 'https://YOUR-DOMAIN.example/sitemap-0.xml' | grep -o '<loc>[^<]*</loc>' | head -3
```

`YOUR-DOMAIN.example`은 실제 대표 도메인으로 바꾼다. 공개 주소에서 수정한 본문과 D2 이미지가
보이고, 전역 검색이 동작하며, 덱별 마지막 수정일이 Git 이력과 맞는지도 확인한다.

## 접근을 제한하고 싶을 때

Pages로 배포한 사이트는 기본적으로 주소를 아는 사람이 열 수 있다. **Cloudflare Access**는
사이트를 보여 주기 전에 방문자를 인증하고, 허용한 사람에게만 접근을 열어 주는 기능이다.
본인 이메일 하나만 허용하고 **One-time PIN**을 로그인 방법으로 사용하면, 이메일로 받은
일회용 코드를 입력해 접속할 수 있다. Starlight에 로그인 기능을 직접 만들 필요는 없다.
[이메일 PIN 설정 방법](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/)을 따른다.

### 운영 주소와 미리보기 주소를 모두 보호한다

Pages의 **Enable access policy**는 처음 켰을 때 미리보기만 보호한다.
`프로젝트.pages.dev` 운영 주소와 별도로 연결한 도메인까지 자동으로 잠기는 것은 아니다.
[미리보기 접근 제한 문서](https://developers.cloudflare.com/pages/configuration/preview-deployments/#customize-preview-deployments-access)에서 이 범위를 확인할 수 있다.

| 보호할 주소 예시 | 용도 |
|---|---|
| `study-notes.pages.dev` | 운영 사이트 |
| `*.study-notes.pages.dev` | 배포별 미리보기·브랜치 주소 |
| `notes.example.com` | 별도로 연결한 도메인이 있을 때 |

다음은 [운영 주소까지 Access를 적용하는 공식 절차](https://developers.cloudflare.com/pages/platform/known-issues/#enable-access-on-your-pagesdev-domain)다.
예시 프로젝트 이름과 도메인은 실제 값으로 바꾼다.

<Steps>

1. Cloudflare의 **Workers & Pages → 해당 프로젝트 → Settings → General → Enable access policy**를 켠다.

2. 생성된 정책의 **Manage**로 Access 애플리케이션을 열고 **Configure**를 선택한다.

3. **Public hostname → Subdomain**에서 맨 앞의 와일드카드 `*`를 제거하고 저장한다.
   보호 대상이 `*.study-notes.pages.dev`에서 `study-notes.pages.dev`로 바뀐다.
   저장 오류가 나면 애플리케이션 이름도 바꿔 본다.

4. Pages 설정으로 돌아와 **Enable access policy를 다시 켠다.**
   운영 주소와 미리보기 주소를 보호하는 Access 애플리케이션이 각각 있는지 확인한다.

5. 별도 도메인이 있다면 **Zero Trust → Access controls → Applications → Create new application → Self-hosted and private**에서
   **Add public hostname**으로 그 도메인도 추가한다. 사이트 전체를 보호하도록 경로는 비워 둔다.

6. 각 애플리케이션에 로그인 방법 **One-time PIN**을 사용할 수 있게 하고,
   허용 정책을 **Action: Allow → Include: Emails → 본인 이메일 주소 하나**로 설정한다.
   다른 사람을 허용하는 기존 규칙이나 인증을 건너뛰는 `Bypass`가 남아 있지 않은지도 확인한다.

</Steps>

이메일 조건은 `@example.com` 같은 도메인 전체가 아니라 본인의 정확한 주소로 제한한다.
`One-time PIN` 자체를 Include 조건으로 추가하면 다른 이메일 사용자까지 허용할 수 있다.
[Access 정책 예제](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/common-policies/)의 이메일 제한 원칙을 따른다.

### PIN은 들어갈 때마다 입력하지 않는다

한 번 인증하면 브라우저에 **로그인 세션**이 유지된다. 같은 브라우저에서 세션이 유효한 동안은
탭을 닫았다가 다시 열어도 PIN을 다시 입력하지 않는다. 기본 전역·애플리케이션 세션은 24시간이며,
7일이나 최대 1개월로 조정할 수 있다.
[세션 관리 문서](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/)가 각 설정의 기준이다.

예를 들어 같은 브라우저에서 한 달간 인증을 유지하려면 다음 세 곳을 맞춘다.

| 설정 위치 — Zero Trust → Access controls 기준 | 예시 값 |
|---|---|
| Access settings의 전역 세션 | 1개월 |
| Applications → 해당 애플리케이션 → Configure의 Session Duration | 1개월 |
| 연결한 정책의 Session Duration | Same as application |

애플리케이션 세션이 끝나도 전역 세션이 유효하고 허용 조건을 만족하면 자동 갱신될 수 있다.
둘 다 만료되거나 쿠키를 지웠을 때, 새 기기·브라우저에서 접속할 때는 다시 인증한다.
세션을 길게 잡으면 인증 횟수는 줄지만, 로그인된 브라우저로 접근할 수 있는 기간도 길어진다.

### 적용 결과를 확인한다

시크릿 창에서 운영 주소·미리보기 주소·별도 도메인을 각각 연다. 인증 전에는 본문이 보이지 않고,
본인 이메일로 PIN 인증을 마치면 본문·검색·이미지가 동작해야 한다. 허용하지 않은 이메일은
사이트를 열 수 없어야 한다. 로그인 화면에 코드를 보냈다는 안내가 나와도, 허용되지 않은
이메일에는 실제 PIN이 발송되지 않는다.

Access는 배포 사이트의 접근을 제한한다. **GitHub 저장소가 공개라면 문서 원본은 계속 공개**되므로,
내용 자체를 본인만 보려면 저장소의 공개 범위도 확인한다. 다시 공개하려면 각 주소에 적용한
Access 보호를 해제하고, 로그아웃 상태에서 접근되는지 확인한다.

## 확인할 제한

- 빌드 이미지의 기본 Node 버전은 바뀔 수 있다. 이 저장소는 `.nvmrc`로 24를 지정한다.
- cold build는 GitHub release에서 D2를 내려받아야 하므로 외부 네트워크가 막히면 실패한다.
- Git 연동에 쓰는 GitHub 앱 권한은 저장소 단위로 준다. 조직 저장소는 조직 관리자의 승인이 필요할 수 있다.

## 이해 확인

배포는 되는데 랜딩의 모든 덱이 같은 날짜로 보인다. 무엇을 의심할까? `prebuild`가 전체 이력을
못 받은 경우다. 빌드 로그에서 "얕은 Git 이력을 전체 이력으로 확장합니다" 줄이 있는지 보고,
Build command가 `npm run build`인지 확인한다. `astro build`만 실행하면 이력 준비를 건너뛴다.
이미 전체 이력이 있으면 확장 로그가 나오지 않으므로, 그 로그가 없다는 이유만으로 실패를 단정하지 않는다.
