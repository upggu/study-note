# 콘텐츠 작성 규칙

페이지는 전부 `.mdx`로 만든다. 독자가 세부 용어를 만나기 전에 **전체에서 지금 어디를 보는지**부터
알 수 있어야 한다. 이 문서는 학습 페이지를 쓰는 AI가 따르는 규칙이고, 사이트 구조·컴포넌트 구현은
[starlight-changes.md](starlight-changes.md)가 맡는다.

## 사이트 구조와 화면 명칭

작업 요청·본문·결과 보고에서 쓰는 명칭의 정본은
[화면 명칭과 AI에게 수정 요청하기](../src/content/docs/starlight/site-vocabulary.mdx)다.
**덱**은 한 주제의 문서 전체, **사이드바 그룹**은 덱 사이드바에서 묶인 페이지들, **페이지**는 고유 URL 하나다.
페이지 안은 **절·하위 절·코드 블록·표·그림**으로 부른다. **덱 사이드바**는 페이지 사이 이동,
**페이지 목차(TOC)**는 절 사이 이동이고, **사이트 홈(랜딩)**과 **덱 개요**는 구별한다.
수정 위치는 페이지 URL과 절 제목으로 좁힌다. 사용자가 다른 표현을 써도 문맥으로 식별되면
이 명칭에 대응시켜 진행하고, 용어를 다시 말해 달라고 요구하지 않는다.

## 작성과 의미 리뷰

아래 절차는 계획 문서가 있든 없든 수행한다. 계획 파일을 만들지는
[AGENTS.md의 작업 계획](../AGENTS.md#작업-계획)을 따른다.

1. **독자·질문·범위부터 정한다.** 독자가 이미 아는 것, 이 페이지가 답할 질문, 읽은 뒤 할 수 있는 일을
   짧게 적는다. 덱 단위 기준은 `_baseline.md`에 둔다([덱 메타데이터](#덱-메타데이터)).
2. **근거와 최소 예제를 확인한다.** 제품 기능은 공식 자료·설치된 버전과 대조하고, 저장소 동작은
   실제 파일·명령으로 확인한다. 제품 보장, 이 저장소의 선택, 설명용 가정, 미확인을 구분한다.
   실행 예제에는 준비 조건·파일 위치·입력·예상 결과를 두고, 상태를 바꾸면 복구 방법도 적는다.
   생략한 코드는 설명용 발췌라고 밝힌다.
3. **학습 순서를 잡는다.** [왜를 남긴다](#왜를-남긴다)의 네 질문 순서로 선행 개념을 연결한다.
   중심 질문이 둘이면 절이나 페이지를 나눈다.
4. **작성한다.** 아래 규칙을 적용하되 절 개수·분량·표·그림 수를 목표로 삼지 않는다.
5. **의미를 리뷰한다.** 아래 표를 본문·예제·근거와 대조하고 핵심 오류·빠진 전제·실행 불가능한 예제를
   고친다. 문장 교정만으로 리뷰를 마치지 않는다.
6. **기술 검증을 수행한다.** [검증 지침](verification.md)의 변경별 범위만 실행하고,
   실행한 명령·관찰·남은 제한을 기록한다.

| 리뷰 질문 | 확인할 증거 |
|---|---|
| 첫 화면만 읽어도 결론과 왜 필요한지가 보이는가 | Thesis 불릿이 중심 질문에 답하고 첫 문단·description과 어긋나지 않는다 |
| 결론에 이르는 원리를 설명했는가 | 문제와 해법을 잇는 예·흐름·비교가 있고 낯선 용어는 쓰는 자리에서 푼다 |
| 선택 이유와 버린 대안이 있는가 | 설계·선택 절에 결정 기준과 대안이 있고, 제품의 선택과 저장소의 선택을 구분했다 |
| 읽고 나서 할 일이나 판단 기준이 있는가 | Thesis 불릿 하나와 페이지 끝에 독자가 실행하거나 판단할 내용이 있다 |
| 설명을 적용하고 결과를 판단할 수 있는가 | 입력과 예상 출력·관찰 기준이 연결되고 예제가 실제 환경과 맞는다 |
| 흔한 오해나 적용 조건을 빠뜨리지 않았는가 | 제품 기능과 운영 권장을 구분하고 유사 개념의 차이를 사례로 짚는다 |
| 검색으로 와도 이해할 수 있는가 | 선행 개념 링크가 있고 번호·앞 페이지 기억에 의존하지 않는다 |
| 이해를 확인할 수 있는가 | 적합한 페이지에 짧은 질문·변형 과제와 답의 근거가 있다 |
| 더 짧고 쉽게 쓸 수 있는가 | 불필요한 용어·반복·곁가지가 없고 [길이 상한](#문장과-문단)을 지켰다 |
| 특정 조직의 사실이 드러나지 않는가 | 실제 이름·수량·현황 대신 가정과 예시 값을 썼다([사내 정보](#사내-정보를-적지-않는다)) |

문서 종류별 기준 예:

- **개념:** "왜 페이지 순서를 파일명에 넣지 않는가?"에 삽입 시 URL 변경 문제를 설명하고
  `sidebar` 배열 대안을 보여 준다.
- **실습:** 임시 덱을 어디에 어떤 파일로 만드는지 보여 주고, 검사 성공을 관찰한 뒤 폴더를 제거하는
  복구까지 둔다.
- **참조:** MDX 오류 표는 증상 → 원인 → 고칠 위치를 연결한다. 모든 행에 퀴즈를 붙이지 않는다.

리뷰 보고에서는 본문에 적은 검증 명령과 실제 실행한 것을 구분한다. 컴포넌트 존재와 검사 통과는
형식 증거이지 학습 효과의 증거가 아니다.

## 기존 페이지에 적용하는 시점

이 문서의 규칙은 새 페이지에 전부 적용한다. 기존 페이지에는 수정 종류에 맞는 것만 적용하고,
수정 대상이 아닌 페이지를 규칙에 맞추려고 일괄 수정하지 않는다.

| 수정 종류 | 적용하는 것 |
|---|---|
| 오탈자·링크·사실 한 줄 수정 | frontmatter 정리만. `reviewedAt`·`status`가 있으면 둘을 함께 지운다 |
| 절 추가·내용 개편 | 위에 더해 서술 규칙 전부. `<Thesis>` 추가와 `legacyThesis` 제거, [길이 상한](#문장과-문단), [왜 네 답](#왜를-남긴다), 말미 `요약` 제거 |
| 페이지 이름·번호 정리 | 별도 개편 범위로 잡는다. 들어오는 링크와 옛 URL·절 북마크도 함께 처리한다. 새 페이지를 끼우거나 지울 때 주변 번호를 다시 매기지 않는다 |

## 사내 정보를 적지 않는다

이 사이트는 공개 주소로 배포된다. 소유자의 회사·팀에만 해당하는 사실은 본문·`_baseline.md`·`_deck.mjs`
어디에도 적지 않는다. 요청이나 참고 자료에 사내 맥락이 섞여 있어도
**어느 조직에나 통하는 가정과 예시**로 바꿔 쓴다.

| 적지 않는 것 | 대신 쓰는 것 |
|---|---|
| 회사·계열사·조직·팀·사람 이름, 내부 시스템·제품·프로젝트 이름 | 역할 이름(플랫폼 팀, IdP 운영팀, 사내 포털) |
| 내부 URL·호스트명·IP·계정, 사내 자료의 파일 이름 | `example.com`·`*.example.internal`·`corp.local` 같은 예시 값과 사설·문서용 IP 대역 |
| 보유 장비 대수, 구매·도입 계획, 라이선스·계약, 비용 | 수량 없는 예시 환경("GPU 서버 여러 대"). 기술적으로 필요한 단위(8-GPU 서버, 2대 pair)는 쓴다 |
| 진행 중인 검토·결정·일정("지금 검토 중", "도입 예정", "운영 중") | "이 덱은 ~를 가정한다", "예시 구성" |
| 사내 절차·양식·보안 규정의 구체 내용 | 공식 문서로 설명할 수 있는 일반 절차 |
| 사내에서만 통하는 약어·용어 | 표준 용어와 풀어 쓴 설명 |
| 요청 대화의 흔적("질문하신", "사용자가 말한") | 질문 자체를 일반 문장으로 |

- 기준은 단어가 아니라 **그 문장이 특정 조직의 사실을 드러내는가**다. "사내 CA", "회사 프록시"처럼
  어느 회사에나 해당하는 일반 시나리오 표현은 써도 된다.
- 덱의 기준 환경은 실제 환경의 기록이 아니라 설명용 가정으로 쓴다. `_baseline.md`에도 실제 수량·현황·
  결정 경위를 적지 않는다.
- 검증 기록에는 OS·도구 버전처럼 재현에 필요한 값만 남긴다. "회사 PC"·"개인 PC" 같은 소유 구분은 적지 않는다.
- 사내 자료를 참고했다면 그 자료의 이름·출처를 적지 않고, 공식 문서로 다시 확인한 내용만 쓴다.
- 사내 사실 없이는 설명이 성립하지 않는 내용은 넣지 않는다. 꼭 필요해 보이면 쓰기 전에 소유자에게 확인한다.

## 설명 순서와 제목

- **`<Thesis>`("결론부터")를 맨 위에 둔다.** 핵심 결론 1~5개 불릿이고, 불릿 하나는 한 문장 한 줄이다.
  목차나 예고가 아니라 중심 질문의 답·판단 기준·꼭 기억할 조건을 쓴다.
- 불릿 중 하나는 그래서 독자가 무엇을 하거나 어떻게 판단할지를 담는다. 근거·예외는 본문으로 보낸다.
- 5개를 채우려고 늘리거나 하위 목록으로 우회하지 않는다. 굵기는 컴포넌트가 입히므로 안에서 `**`를 쓰지 않는다.
  사용 예는 `src/components/docs/Thesis.astro` 머리 주석에 있다.
- **첫 문단은 문제 상황이다.** 어떤 상황에서 무엇이 막히는지 1~3문장으로 적는다.
  "이 페이지는 A·B·C를 다룬다"는 목차 예고는 쓰지 않는다.
- **그다음 큰 그림이다.** 전체 흐름·구성 요소의 역할·앞뒤 페이지와의 관계 중 필요한 것을
  짧은 문단·표·그림 하나로 보여 준다. 제품명·약어·설정값 나열로 열지 않는다.
- **세부 개념은 그 뒤다.** 새 용어·약어는 처음에 풀 이름을 쓰고, 새 개념은 없으면 생기는 문제 → 해법 순으로 설명한다.
- `<TermIntro>`에는 큰 그림을 읽는 데 꼭 필요한 용어만 둔다. 설치·운영 용어는 실제로 쓰는 절 앞으로 미룬다.
  이 상자는 기본으로 접혀 있다.
- 정착된 영어 용어는 번역하지 않는다. 제품·스펙 고유 명칭(Declarative Agent 등)은 영어로 두고 처음 나올 때 뜻을 푼다.
- **한 제목 아래 한 개념.** 요약 한 줄로 절을 설명할 수 없으면 나눈다. 페이지가 길어지면 같은 사이드바
  그룹의 여러 페이지로 나눈다.
- h2는 주요 주제, h3는 세부다. h4는 목차에 잡히지 않으므로 쓰지 않는다. 제목을 바꾸면 앵커도 바뀐다.
- 페이지 끝에 `요약` 절로 결론을 반복하지 않는다. 이해 확인·다음 페이지 안내·참고 자료는 필요하면 둔다.
- 핵심 원칙은 `:::tip[…]`, 함정은 `:::caution[함정]`을 쓴다.

### 왜를 남긴다

동작 설명만 있는 페이지는 나중에 읽으면 "그래서 왜?"가 남는다. 페이지마다 아래 네 질문의 답이
본문 어딘가에 있어야 한다. 고정 제목으로 두지 않고 결론부터·첫 문단·본문·끝에 나눠 담는다.

| 질문 | 보통 두는 자리 | 없으면 생기는 일 |
|---|---|---|
| 어떤 상황에서 무엇이 막히는가 | 결론부터 아래 첫 문단 | 독자가 자기 문제와 연결하지 못한다 |
| 이것이 없으면 무슨 일이 생기는가 | 개념·구성 요소를 소개하는 절의 첫머리 | 기능 목록으로 읽히고 기억에 남지 않는다 |
| 대안 대신 왜 이것을 골랐는가 | 선택·설계를 설명하는 절. 버린 대안과 결정 기준을 한두 문장으로 | 다른 상황에서 같은 선택을 반복할지 판단할 수 없다 |
| 그래서 독자는 무엇을 하거나 어떻게 판단하는가 | 결론부터 불릿 하나와 페이지 끝 | 읽고 나서 할 일이 없는 설명으로 끝난다 |

```text
나쁜 순서: 제품 A의 컴포넌트 이름 8개 → 설정 파일 → 이 제품이 푸는 문제
좋은 순서: 사용자가 겪는 문제 → 전체 흐름과 역할 → 제품이 맡는 자리 → 컴포넌트와 설정
```

제품의 선택과 이 저장소의 선택을 구분한다. 제품이 그렇게 만든 이유는 공식 자료로 뒷받침하고,
이 저장소나 예시 환경의 선택은 그렇게 쓴 이유와 조건을 적는다. 이유를 확인하지 못했으면
"확인하지 못했다"고 적고 추측을 이유처럼 쓰지 않는다.

참조 성격의 페이지(오류 표·명령 목록·필드 설명)는 네 답을 전부 요구하지 않는다. 첫 문단의
문제 상황과 "언제 이 표를 보는가" 정도면 충분하다.

### 문장과 문단

짧고 분명하게 쓴다. "짧게"는 해석이 갈리므로 아래 상한으로 스스로 검사한다.
본문 전체를 불릿으로 바꾸지는 않는다. 이 사이트는 슬라이드가 아니라 참조용 문서이고,
원리를 잇는 설명은 짧은 산문이 불릿 조각보다 나중에 읽기 쉽다.

- **문단은 3문장 이내, 한 문단 한 생각.** 한 문장은 한 가지 주장만 담는다.
  "~고", "~며", "~인데"로 절을 두 번 이상 이으면 문장을 나눈다.
- **나란한 항목만 불릿으로 쓴다.** 선택지·조건·절차·비교처럼 같은 층위의 항목이 목록이다.
  불릿 하나는 2문장 이내이고, 앞머리를 굵게 해 무엇에 관한 항목인지 보이게 한다.
- 중첩은 한 단계까지만 쓴다. 원리를 풀어 설명하는 자리는 문단으로 쓴다.
- **괄호 속 경로·함수명은 문장 밖으로 뺀다.** 근거가 되는 파일·함수는 문단 끝 한 줄이나 표·`근거` 절로 옮긴다.
- **같은 내용을 두 번 쓰지 않는다.** 결론부터에 쓴 말을 첫 문단에서, 절 첫 문장에 쓴 말을 절 끝에서 반복하지 않는다.

```text
전: Paseo는 provider에 자기 토큰으로 로그인하지 않는다. 각 코딩 에이전트의 CLI를
    자식 프로세스로 띄우고, 그 CLI가 자기 로그인 저장소를 읽어 AI 회사 API를 부른다.
후: 데몬은 토큰 없이 에이전트 CLI만 띄우고, API 호출은 CLI가 자기 로그인으로 한다.
```

## 시각 자료와 외부 이미지

분리한 D2 원본은 사용하는 덱의 `_d2/`에 둔다. 덱 폴더만 복사해도 원본이 따라가도록 하고,
참조 문법은 [D2 작성 규칙](d2-authoring.md#펜스-속성)을 따른다. SVG는 빌드가 생성하므로 원본 대신 복사하지 않는다.

텍스트만으로 머릿속에 모양을 만들기 어려운 내용에는 시각 자료를 붙인다. 특히 다음은 그림의 효과가 크다.

- 시스템 전체 구조와 데이터 흐름
- 요청·이벤트의 시간 순서와 상태 변화
- 제품의 실제 화면, 트레이스 워터폴, 대시보드, 개발 도구 UI
- 저장 형식·계층·공간 배치처럼 위치 관계가 중요한 개념
- 둘 이상의 방식이나 전후 상태를 나란히 비교하는 경우

| 보여줄 것 | 우선 수단 |
|---|---|
| 관계·시퀀스·상태·아키텍처·흐름 | `d2` 펜스. 강조·툴팁·링크·단계 탭·폭 측정은 [D2 작성 규칙](d2-authoring.md)을 따른다 |
| 단계별 메시지·객체의 보관 상태 비교 | D2 단계 탭 + 상태 표, 긴 순서는 Steps — [선택 기준](d2-authoring.md#ai의-선택-순서) |
| D2 미지원 타입(timeline 등) | 표, 또는 형태를 재설계한 D2 |
| 실제 제품이 어떻게 보이는가 | **공식 문서의 스크린샷** |
| 복잡한 공식 아키텍처·데이터 형식 | **공식 구조도** |
| 반복 필드와 정확한 비교 | 표 |
| 코드로 직접 보여줄 수 없는 질감·현장·물체 | 출처가 분명한 외부 이미지 |

상호작용·애니메이션은 이해를 도울 때 쓰되 독자가 정지·선택할 수 있게 한다. 단계가 많으면 설명을
나누고 Steps와 상태 표로 전체 순서를 함께 남긴다.

외부 이미지는 다음 원칙을 모두 지킨다.

1. **공식 문서·원 저작자 자료를 우선한다.** 검색 결과 썸네일이나 출처를 거슬러 올라갈 수 없는
   재업로드 이미지는 쓰지 않는다.
2. 원격 URL을 그대로 임베드하지 않고 `public/images/<덱>/`에 사본을 둔다. 원본 사이트의 장애·개편,
   핫링크 차단 때문에 문서가 깨지는 일을 막기 위해서다.
3. 이미지 아래에 **이 그림에서 어디를 봐야 하는지**를 한두 문장으로 적는다. 현재 문맥에 필요한 부분만 가리킨다.
4. **원본이 실린 페이지 링크와 출처 이름을 함께 둔다.** 이미지 파일만 링크하지 않는다.
5. `alt`에는 "그림"이 아니라 그림이 전달하는 핵심 관계를 쓴다. 장식 이미지는 넣지 않는다.
6. 원본 `width`·`height`를 지정해 공간을 예약하고, 모바일에서 본문이 가로로 넘치지 않는지 확인한다.

외부 이미지는 공용 `<SourceFigure>`를 사용한다. 이미지를 누르면 확대 dialog가 열리고, 캡션의 출처 링크는
원문 페이지로 간다.

```mdx
import SourceFigure from '../../../components/docs/SourceFigure.astro';

<SourceFigure
  src="/images/<덱>/example.png"
  alt="요청이 수집기를 거쳐 세 저장소로 나뉘고 조회 화면에서 다시 합쳐지는 구조"
  width={1600}
  height={900}
  caption="지금은 가운데 수집기에서 세 저장소로 갈라지는 화살표만 본다."
  sourceHref="https://example.com/official-documentation/page"
  sourceLabel="제품 공식 문서 — Architecture"
/>
```

## 프론트매터

모든 페이지의 필수 frontmatter는 `title`과 `description`이다. 페이지 소속·읽는 순서는
같은 덱의 `_deck.mjs`에서 관리하며 본문에는 적지 않는다.

```yaml
title: "요청 경로"
description: 요청이 각 구성 요소를 지나는 순서
```

- 사이드바 라벨은 `title`에서 온다. 제목·파일명·URL에 순서 번호를 넣지 않는다.
  예: `ServiceAccount — Pod의 신원`, `service-account.mdx`, `/<덱>/service-account/`.
- 내부 링크·이미지에는 `/starlight/intro/`처럼 **base 없는** 사이트 경로를 쓴다. 빌드가 base를 붙인다.
  배포 저장소 이름을 본문·`_deck.mjs`에 넣지 않는다. 변환 범위와 새 컴포넌트의 처리는
  [루트와 하위 경로 배포](starlight-changes.md#루트와-하위-경로-배포)에 있다.
- `deckGroup`·`sidebar.order`는 사용하지 않는다. 남아 있으면 콘텐츠 검사가 실패한다.

새 본문 페이지에는 `<Thesis>`를 둔다. `legacyThesis: true`는 규칙 도입 전 페이지의 이관 표시일 뿐
새 페이지에 쓰지 않는다. 기존 페이지에 `<Thesis>`를 추가하면 이 필드를 제거해야 `npm run check`가 통과한다.

`reviewedAt`·`status`는 더 쓰지 않는 필드다. 새 페이지에 넣지 않고 기존 값을 갱신하지 않는다.
기존 페이지는 [적용 시점](#기존-페이지에-적용하는-시점)에 따라 둘을 함께 지운다. `status`만 남기면
검사가 실패한다. 확인한 날짜·버전을 남겨야 하면 본문이나 덱 `_baseline.md`에 적는다.

다른 이름으로도 찾을 수 있어야 할 때만 `aliases`를 추가한다. 본문 앞에 표시되어 Pagefind 검색 대상이 된다.
덱 index의 별칭은 `_deck.mjs`의 `aliases`에 둔다.

```yaml
aliases: [옛 이름, 약어, 동의어]
```

개념·제품의 소개 시점을 기록할 때는 `introduced`를 쓴다. `month`는 `YYYY-MM`, `event`는 날짜가 가리키는 사건,
`source`는 그 시점을 확인한 공식 URL이다. 페이지 상단에 연월과 출처 링크가 자동으로 표시된다.
문서 작성일과 혼용하지 않는다.

```yaml
introduced:
  month: "2026-09"
  event: System One Models·Jev 소개 및 early access 공개
  source: https://typesafe.ai/blog/introducing-system-one-models-and-jev
```

## 덱 메타데이터

`_deck.mjs`의 `sidebar`에 그룹 이름과 페이지 목록을 적는다. 다음은 목차 부분만 발췌한 예다.

```js
sidebar: [
  {
    label: '구조 이해',
    pages: ['overview', 'request-flow', 'components'],
  },
  {
    label: '운영',
    pages: ['deployment', 'troubleshooting'],
  },
],
```

- 그룹은 `sidebar` 배열 순서, 그룹 안 페이지는 `pages` 배열 순서로 표시한다. 별도 ID·정렬 숫자는 없다.
- `pages`에는 `.mdx`를 뺀 덱 상대 경로를 쓴다. `advanced/setup.mdx`는 `advanced/setup`이다.
- 모든 본문은 정확히 한 번 등록한다. 누락·중복·없는 파일·빈 그룹은 검사에서 실패한다.
- 덱 `index.mdx`는 맨 앞에 자동으로 추가되므로 목록에 적지 않는다.
- 순서만 바꾸면 URL은 유지된다. 파일명을 바꾸면 `sidebar`·`map`·본문 링크를 함께 확인한다.

덱마다 `category`(4종) 하나와 `tags` 목록을 정한다. 카테고리는 "어디부터 볼지" 고르는 굵은 묶음이고,
카테고리를 가로지르는 주제(쿠버네티스·LLM·인증 같은)는 태그가 맡는다. 어휘는 `src/data/catalog.mjs`가 전부다.
**태그는 그 덱이 실제로 여러 페이지에 걸쳐 다루는 주제만 붙인다.** 해당하는 태그가 없으면 `tags: []`로 두고,
어휘를 새로 추가하면 최소 한 덱이 그걸 써야 한다. `catalogOrder`가 랜딩 카드 순서, `navOrder`가 topic 전환 순서다.
`label`은 헤더의 현재 덱 이름·topic 사이드바·랜딩 덱 항목이 함께 쓰는 유일한 덱 이름이다.
랜딩은 그 옆에 `(slug)`를 붙여 URL 경로를 보여 주므로 별도 제목 필드는 없다.

`termIntro`는 기본으로 생략한다. 새 개념 학습 덱만 `termIntro: 'required'`로 두면 학습 본문 페이지 첫머리의
`<TermIntro>`를 검사한다. `index`, `glossary`·`*-glossary`, `wrapup`·`*-wrapup`은 제외한다.
형식은 `src/components/docs/TermIntro.astro` 머리 주석에 있다.

`_baseline.md`에는 독자·선행 지식·학습 결과, 포함/제외 범위, 기준 버전, 덱 전용 서술 규칙을 둔다.
실제 수량·현황·결정 경위는 적지 않는다. 그 덱을 개편할 때 갱신하고, 기존 덱을 형식에 맞추려고
일괄 수정하지 않는다.

## 근거와 참고 자료

사실·버전·수식·현재성 있는 주장처럼 나중에 재확인할 내용에는 **공식 문서나 원 논문 중심의 참고 링크**를 둔다.
링크는 말미에 모으지 말고 **그 주장이 있는 문장에 바로 건다.** 페이지 말미의 `## 참고 자료`는 본문 흐름에
넣기 어려운 추가 읽을거리만 두는 보조 절이고, 각 링크에서 무엇을 확인할 수 있는지 짧게 적는다.

**외부 링크는 새 탭에서 열린다.** 독자가 원문을 보면서 페이지로 돌아와야 하기 때문이다. 작성자는 일반
마크다운 링크 `[이름](https://…)`만 쓰면 빌드의 `rehypeExternalLinks`가 `target="_blank"`를 붙인다.
`<LinkCard>`·`<LinkButton>`처럼 컴포넌트에 외부 URL을 줄 때는 rehype가 닿지 않으므로 `target="_blank"`를 직접 적는다.

도구 설치는 **긴 설치 커맨드·스크립트를 본문에 복사하지 않는다.** 공식 설치 페이지 링크를 걸고,
본문에는 설치 확인 명령과 이 덱에서 실제로 쓰는 옵션·설정만 둔다.

별도 원문이 없는 내부 절차나 작성자의 정리에는 억지로 링크를 넣지 않는다. 어떤 주장과 연결되는지
알 수 없게 URL만 나열하지 않는다.

## 강조와 CommonMark 함정

- 닫는 `**` 앞에 따옴표·괄호·`%`·백틱을 두고 바로 뒤에 한글 조사를 붙이지 않는다.
  - `**"조회 → 해결"**의` → `"**조회 → 해결**"의`
  - `**커리큘럼의 25%**가` → `**커리큘럼의 25%가**`
  - `` **`get all`**이다 `` → `` `get all`이다 ``
- 한 문단이나 표 한 칸에 범위 표시 `~`를 두 번 쓰지 않는다. GFM이 그 사이를 취소선으로 해석할 수 있다.
- raw HTML을 본문에 인라인으로 쓰지 않는다. 강조는 `**`와 aside를 사용한다.

## 컴포넌트

산문으로 길게 풀기 전에 내장 컴포넌트로 구조화할 수 있는지 먼저 본다. **모양이 정해진 정보는 그 모양의
컴포넌트**에 담는다. 공용 문서 컴포넌트는 `src/components/docs/`에 있고, 기존 컴포넌트를 먼저 확인한다.

| 컴포넌트 | 쓸 자리 |
|---|---|
| `<Steps>` | 순서가 있는 절차 |
| `<Tabs>` | 차이만 보여주고 싶은 두 갈래 |
| `<CardGrid>` + `<Card>` | 층·분류의 개요 |
| `<FileTree>` | 디렉터리 구조. `- 경로/` 뒤에 설명을 이어 쓰면 주석이 되고 중요한 파일은 `**굵게**` 한다 |
| `<LinkCard>` | 페이지 끝의 다음 페이지 안내 |
| `<LinkButton>` | 덱 index의 첫 페이지로 가는 CTA — 덱마다 하나 |
| `<Badge>` | 성숙도·deprecated·기본값·시험 비중 같은 짧은 상태 |
| `<DeckMap>` | 덱 index의 "구성" 절 — 덱마다 하나 |
| `<Thesis>` | 페이지 첫머리의 "결론부터" — 페이지마다 하나 |
| `<SourceFigure>` | 외부 이미지 — 읽을 지점·대체 텍스트·원문 출처 포함 |
| `<ExternalLink>` | 쓰지 않는다. 외부 링크는 일반 마크다운 링크로 쓰면 빌드가 새 탭으로 연다([근거와 참고 자료](#근거와-참고-자료)) |
| `d2` 펜스 | 다이어그램 — [시각 자료](#시각-자료와-외부-이미지) |

OS별 커맨드를 여러 절에서 반복해 보여줄 때는 `<Tabs syncKey="operating-system">`로 동기화한다.
모든 그룹의 `<TabItem>` label을 정확히 `macOS`, `Ubuntu`로 맞춘다. label이 다르면 동기화가 깨진다.
OS별 절차를 만들 때 이 방식으로 묶는다.

## 덱 index

덱 index의 첫 화면에는 **이 덱이 왜 필요한가(배경)와 무엇을 다루는가(내용 요약)**가 드러나야 한다.
페이지 제목 나열은 요약이 아니다. 어떤 문제의식에서 출발했고 읽고 나면 무엇을 알게 되는지를 짧은 문단으로 먼저 쓴다.

덱 index에는 `<LinkButton>`과 `<DeckMap>`을 각각 하나 둔다. 구성도에는 D2 대신
`<DeckMap deck="<덱 slug>" />`를 쓰고, 단계 내용은 같은 폴더의 `_deck.mjs`에 한 번만 적는다.
props는 `src/components/docs/DeckMap.astro` 머리 주석에 있다.

## MDX에서 자주 깨지는 것

- JSX 안의 마크다운은 들여쓰기하지 않는다. `<Card>`·`<TabItem>` 태그와 내용을 0칸에 두고 빈 줄로 띄운다.
- `<Steps>` 안 번호 목록에 딸린 코드 블록만 3칸 들여쓴다.
- 제목에 `<Badge>`를 붙일 때 공백 없이 쓴다. 공백이 있으면 앵커 slug 끝에 `-`가 붙는다.
- 덱 밖 페이지만 topic plugin의 `exclude`에 추가한다.
- 코드 펜스 언어는 하이라이터가 지원하는 이름만 쓴다. 전용 문법이 없으면 `text`를 쓴다.
