# 작업 계획 관리

[coding-agents의 계획 문서 가이드](../../src/content/docs/coding-agents/exec-plans.mdx)를
이 저장소에 적용한 공통 규칙이다. **계획 파일을 언제 만드는지는
[AGENTS.md의 작업 계획](../../AGENTS.md#작업-계획)이 정본이다.** 이 문서는 만들기로 한 계획의
번호·상태·기록·완료 절차만 다룬다.
개별 계획은 이 문서를 링크하고 공통 수명주기를 복사하지 않는다.

## 계획 찾기

폴더가 전체 진행 상태를 말한다. `active/`에 있는 파일이 미완료 계획의 전부이고, 끝나면
`completed/`로 옮긴다. README에는 관리 규칙만 두고 목록을 중복 기록하지 않는다.
제목·지금 위치·결정·검증 결과는 각 계획이 정본이다.

```bash
ls docs/exec-plans/active/
```

미완료 계획이 없으면 출력이 비어 있다. 차단 사유와 지금 위치가 필요하면 해당 파일 머리를 읽는다.
완료 계획은 `docs/exec-plans/completed/`에 번호순으로 있다.

## 번호와 파일명

- 새 계획은 `active/`에 만든다. `active/`와 `completed/`의 파일을 함께 확인하고,
  사용한 최대 번호 다음 번호를 발급한다.
  파일명 번호는 네 자리로 쓴다. 가상 예시로 `0001-json-basics.md`의 제목은 `# 1. JSON 기초 덱`처럼
  앞의 0을 생략한다.
- 완료·취소된 번호도 재사용하지 않고 기존 계획 번호를 다시 매기지 않는다.
- 같은 작업의 보조 문서는 `0001-json-examples.md`처럼 같은 번호를 쓰고 주 계획과 서로 링크한다.
  독립된 목표는 새 번호를 쓴다.
- 계획 번호는 작업 식별자이며, 학습 페이지의 번호 없는 명명(AGENTS.md의 콘텐츠 원칙)과 별개다.
- 지침·본문에서 계획 파일명을 설명할 때는 특정 과거 작업 대신 가상 예시를 쓴다.
- 파일명을 바꾸거나 폴더를 옮기면 저장소의 링크와 재개용 요청문도 함께 확인한다.
  이동은 `git mv`로 해서 이력을 잇는다.

## 상태와 실행 범위

완료 여부는 폴더가 말하므로 머리에 `완료` 상태 줄을 따로 두지 않는다. 진행 중 계획에는
지금 위치를, 멈춘 계획에는 `상태: 차단`과 필요한 입력·환경·재개 조건을 적는다.
일부 작업이 끝나도 전체 완료 조건이 남으면 `completed/`로 옮기지 않는다.
작업별 checkbox나 `todo/doing/blocked/done` 표는 계획에 맞게 쓴다.
이 기록은 문서 상태이며 별도 도구의 goal 상태를 변경하라는 지시가 아니다.

머리에 지금 위치와 실행 범위를 두고 최신 사용자 요청에 맞춰 갱신한다.

- 조사·계획만: 계획을 작성하고 구현은 시작하지 않는다.
- 특정 작업까지: 해당 작업의 수정·검증·기록까지 완료한다.
- 전체 완료: 허용된 다음 작업을 이어서 끝낸다. 작업 단위가 작다는 이유로 매번 멈추지 않는다.

이미 허용된 작업에 계획 승인을 추가하지 않는다. 새로운 범위 결정과 외부 쓰기는
[AGENTS.md](../../AGENTS.md)를 따른다. 계획 작성은 커밋·푸시·배포 허가를 뜻하지 않는다.

## 작성·실행·재개

작성 전 관련 코드·문서·현재 diff를 확인한다. 모르는 구현값은 미결 사항으로 남기고 이를 판정할
작업을 적는다. 다음 항목을 포함한다.

- 사용자가 얻을 결과, 포함·제외 범위, 관찰 가능한 완료 조건
- 관련 지침·원본 파일·근거 링크
- 작업 ID별 의존성·입력·수정 범위·완료 조건·필요한 검증
- 지금 위치, 실제 결정과 이유, 검증 결과, 미해결 사항, 다음 행동

작업 하나는 독립적으로 완료를 판정할 수 있을 만큼 작게 둔다. 새 세션은 계획 머리와 현재 작업,
관련 지침부터 읽고 `git status`와 diff로 실제 상태를 확인한다.
작업 후에는 checkbox/상태·결정·검증·다음 행동을 같은 계획에 갱신한다.
콘텐츠 작업의 계획에는 페이지별로 중심 질문·문제·수정 또는 유지 이유·근거/실행 결과·남은 제한을 기록한다.
명령을 적어 둔 것과 실행 성공을 구분하고, 미실행 검증은 이유와 재개 명령을 남긴다.
비밀번호·개인키·토큰·실제 개인정보와 긴 원본 로그는 기록하지 않는다.
검증 종류와 범위는 [검증 지침](../verification.md)을 따른다.

## 완료와 영구 문서 반영

1. 전체 완료 조건을 확인하고 아직 필요한 검증만 실행한다. 통과한 검사를 이유 없이 반복하지 않는다.
2. 최종 결과·검증 근거·남은 제한을 완료 기록에 적고 지금 위치 줄을 지운다.
3. 앞으로도 필요한 사실은 제자리로 옮긴다. 덱 버전·범위는 `_baseline.md`, 학습 내용은 본문,
   공통 작성·검증 규칙은 `docs/`의 해당 지침, 실습 사용법은 해당 실습의 README에 반영한다.
   저장소 전체에 반복해서 필요한 행동 규칙만 AGENTS.md에 둔다.
4. `git mv docs/exec-plans/active/<파일> docs/exec-plans/completed/`로 옮기고, 그 계획을 가리키던
   링크를 고친다. 같은 폴더 안의 상대 링크는 그대로지만 폴더를 가로지르는 링크는 경로가 바뀐다.
5. 완료 계획은 당시 실행 기록으로 보존한다. 새 작업의 현재 지침으로 삼거나 진행 로그를 계속 덧붙이지 않는다.

가이드의 예시 구조를 맞추려고 `product-specs/`·changelog·decisions 문서를 일괄 생성하지 않는다.
이 레포의 요구는 각 덱의 `_baseline.md`가, 기술 규약은 `docs/`의 작성·검증 지침이 맡는다.
새 문서는 독립된 관리 필요가 있을 때 만들고, 기존 완료 계획을 새 템플릿으로 재작성하지 않는다.

## 최소 템플릿

```md
# <번호>. <작업 제목>

지금 위치: 탐색 완료 · 구현 미착수 · 다음 M1
실행 범위: 조사·계획만 / 특정 작업까지 / 전체 완료 중 사용자 요청에 맞는 값

[계획 관리 규칙](../README.md)을 따른다.

## 목표와 완료 조건

- [ ] 사용자가 확인할 수 있는 결과

## 범위와 입력

포함·제외 범위, 관련 원본·지침, 확인할 가정

## 작업

| ID | 의존성·입력 | 수정 범위 | 완료 조건·검증 |
|---|---|---|---|
| M1 | ... | ... | ... |

## 실행 기록

| 작업 | 상태 | 결정·변경 파일 | 검증 결과·미해결 사항 | 다음 행동 |
|---|---|---|---|---|

## 완료 기록

최종 결과, 검증 근거, 제한, 영구 문서 반영 위치
```
