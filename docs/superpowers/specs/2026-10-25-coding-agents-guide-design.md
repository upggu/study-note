# coding-agents 요청 중심 가이드 개편

## 의도와 범위

독자는 Git·Markdown·기본 명령 실행을 알고 자신의 프로젝트에 AI를 적용하려는 사람이다.
설치 → 기존 프로젝트 적용 또는 신규 세팅 → 제품 기획 → 개발 → 변경·이어받기를 요청문으로 실행하고 결과를 판단할 수 있게 한다.
개편 방향과 _baseline.md를 포함한 범위는 합의했다. 세부 설계·계획은 검토 초안이며 아직 승인되지 않았다.
2026-10-25 재개 요청에 따라 실제 설치 스킬과 부분 편집을 대조해 이 설계를 수정한다.
builder check와 사용자 설계 승인, writing-plans의 계획 리뷰·확인 후 남은 본문 편집을 재개한다.
현재 계획의 수정은 사용자가 요청한 초안 리뷰이며 승인된 설계에서 작성한 최종 계획으로 간주하지 않는다.
후속 요청에서 기존 문서·목차·페이지 구성의 변경을 허용했다. 아래 구성은 그 제약을 풀어 다시 정리한 제안이다.

PM Skills의 pm-product-discovery가 아이디어 탐색·가정 식별·검증 실험 설계를,
pm-execution의 create-prd가 PRD 작성·리뷰를, superpowers가 개발 설계·계획·구현·검증을 맡는다.
사용자 후속 합의로 pm-product-discovery도 기본 설치 안내에 포함한다. 이 변경은 설계·계획 전체의 실행 승인이 아니다.
덱은 산출물의 보관 위치, 기존 문서 연결, 스킬 간 인계와 지속 문서 갱신만 보완한다.
스킬 내부 절차·양식·파일명을 다시 정의하지 않는다.

## Goals · non-goals · anti-goals

- 기본 경로에서 상황별 요청문·받을 결과·판정 기준을 먼저 찾을 수 있다.
- 설치·지침 로딩, 제품 결정, 설계·계획 승인, 인계 조건은 기본 경로에 남긴다.
- 기본 설치는 superpowers·pm-product-discovery·pm-execution이며, 탐색은 필요한 요청에 적용하고 모든 개발 작업의 필수 선행 단계로 만들지 않는다.
- 세부 구조·ledger·도구 차이·비교는 부록이다. 부록을 읽어야 기본 요청이 실행되는 구조를 피한다.
- overview·필수 제품 README·기능 수에 따른 자동 분리·작은 변경의 파일 생략·추가 리뷰 강제를 없앤다.
- PRD를 별도 요구 ID·상태 관리 양식으로 바꾸거나 다른 도구 조합을 선택하게 만들지 않는다.
- 사이트 UI·배포·공통 설정·다른 덱은 범위 밖이다. 커밋·푸시는 하지 않는다.

## 제약

현재 수정된 추적 파일 8개와 미추적 installation.mdx·project-setup.mdx·product-requirements.mdx를 출발점으로 삼는다.
기존 미커밋 변경을 출발점으로 유효한 결정·설명·예제를 재사용하며, 완료한 조사·편집을 처음부터 반복하지 않는다.
기존 페이지 수·파일·절 구성은 고정하지 않는다. 요청 중심 흐름에 맞춰 통합·분리·삭제·이름과 순서 변경이 가능하다.
현재 내부 링크와 리다이렉트 목적지를 새 구성에 맞춘다. 옛 절 ID 80개를 전부 본문에 남기는 것은 완료 조건이 아니다.
페이지 순서는 _deck.mjs로 관리한다.
사이트 작성 지침·검증 지침을 따른다. 최종 npm run check는 한 번 실행하고 실패나 추가 수정이 있을 때만 반복한다.
새 페이지와 순서 변경만으로 브라우저를 실행하지 않는다.
현재 main 작업 폴더를 유지하고 커밋·푸시는 하지 않는다. 이는 이 저장소 AGENTS.md의 실행 정책이다.
검토 패키지는 커밋 범위 대신 미커밋 diff와 미추적 파일 원문을 포함한다. HEAD..HEAD를 완료 증거로 쓰지 않는다.

## 실제 스킬과 버전별 조건

설치 캐시의 plugin.json과 실제 SKILL.md를 읽었다. 아래 설치 경로는 로컬 검토 근거이며 공개 본문에는
개인 절대 경로 대신 버전·공식 링크·자기 환경에서 확인하는 요청문을 둔다.

| 도구 | 설치 원본 | 확인 결과 |
|---|---|---|
| Codex superpowers | `~/.codex/plugins/cache/openai-curated-remote/superpowers/7.0.1/skills/` | 7.0.1. 이번 개편의 검토·실행 기준 |
| Claude Code superpowers | `~/.claude/plugins/cache/claude-plugins-official/superpowers/7.0.0/skills/` | 7.0.0. 7.0.1과 동일하다고 쓰지 않음 |
| PM Skills pm-execution | 양쪽 도구의 `plugins/cache/pm-skills/pm-execution/2.2.0/skills/create-prd/SKILL.md` | 2.2.0. 두 create-prd 원문은 바이트 단위로 동일 |

- create-prd: 문제·대상 사용자·성공 기준이 부족하면 작성 전에 질문한다. 사용자가 진행을 지시한 경우에만
  부족한 내용을 가정으로 표시해 작성한다. 기존 PRD 리뷰도 같은 스킬이 맡는다. 질문 목록·8절 양식은 복제하지 않는다.
- brainstorming 7.0.1: 맥락을 먼저 읽고 접근법을 합의한 뒤 설계를 작성·승인한다. 설계가 필요한 작은 변경도
  짧은 문서가 대상이다. 7.0.0은 작은 변경의 설명을 대화에서 승인할 수 있다. 두 버전 모두 분명한 요청을
  바로 처리하는 경로가 있으므로 덱이 독자적인 크기 기준이나 파일 생략 예외를 만들지 않는다.
- writing-plans: 두 설치본의 원문이 동일하다. 설계 승인 뒤 계획을 작성·자체 검토하며,
  실행 방식이 이미 지정됐어도 사용자의 계획 리뷰·확인을 기다린다. 도구 조합과 이미 정한 문서 운영은 재선택하지 않는다.
- 실행 스킬: 작업별 의미 검토는 두 경로 모두 유지한다. 별도 작업 리뷰어는 SDD에서만 주 에이전트가
  작성자와 분리해 배정한다. native는 executing-plans에 따라 작업별 별도 리뷰어 없이 최종 전체 리뷰를 수행한다.
  하위 에이전트 도구가 있으면 새 리뷰어를 배정하고, 없으면 최종 self-review와 그 제한을 보고한다.
  SDD의 하위 구현자가 리뷰어를 생성하지 않으며 위임할 수 없는데 독립 리뷰했다고 쓰지 않는다.
- 설치된 파일의 직접 열람과 세션의 자동 발견·전체 실행은 다른 증거다. 이번 확인을 새 프로젝트 실습 성공으로 표현하지 않는다.

기존 공개 링크의 PM Skills 커밋 `07b34f64ee828df08953f505b7f747aef85ae7c6`의 create-prd는
설치된 2.2.0 원문과 바이트 단위로 동일함을 확인했다. 이 확인을 패키지 전체의 동일성으로 확대하지 않는다.
Codex의 migrated `source-command-write-prd`도 읽었지만 기본 안내는 공통으로 create-prd를 이름으로 요청한다.
특정 도구의 slash 명령 이름과 SKILL.md의 호출을 같은 것으로 단정하지 않는다.

pm-product-discovery는 기본 안내에 추가하기로 합의했으며 이번 요청에서 패키지를 설치하지 않았다.
로컬 marketplace 체크아웃의 `pm-product-discovery/.claude-plugin/plugin.json`은 2.2.0이다.
같은 체크아웃의 `skills/brainstorm-ideas-new/SKILL.md`, `skills/identify-assumptions-new/SKILL.md`,
`skills/brainstorm-experiments-new/SKILL.md`,
`commands/discover.md`를 읽어 역할과 PRD 인계를 확인했다. 이는 설치·활성화·실행 성공의 증거가 아니다.
본문 작성 시 사용하는 원문·버전·확인 범위를 밝히며, Codex 공통 요청문에서 `/discover`가 그대로 실행된다고 가정하지 않는다.

## 제품 탐색과 PRD의 연결

기본 설치 대상에 포함하는 것과 모든 요청에서 실행하는 것은 구분한다.
제품 아이디어나 해결 방향을 탐색할 때 pm-product-discovery를 사용하고, 이미 정해진 요구의 개발·버그 수정에는
탐색을 반복하지 않는다. 제품 목적·범위·정책을 다시 판단해야 할 때 필요한 탐색으로 돌아간다.
pm-product-strategy·pm-market-research 등 다른 PM 패키지는 해당 작업이 필요할 때 추가하는 선택 사항이다.

product-requirements에서 탐색 요청과 PRD 작성·리뷰 요청을 구분한다. 탐색 결과에서는 후보와 선택 이유,
핵심 가정·기존 근거·검증할 실험과 판정 기준을 확인한다. 실험 설계는 실험 실행이나 가정 검증 완료가 아니다.
탐색만 요청하면 결과와 다음 판단에 필요한 정보를 제시하고 멈춘다. 실제 인터뷰·실험 실행·외부 반영은
별도 요청 범위와 허용을 따른다. PRD까지 요청했다면 확인된 제품 맥락과 남은 가정을 create-prd에 넘기되,
그 스킬의 정보 부족 시 질문 조건을 유지한다. 개발 설계·구현은 요청 범위에 포함된 경우에만 이어 간다.

기존 PRD의 **리뷰만** 요청하면 create-prd의 기준으로 결정에 필요한 누락을 먼저, 줄일 내용을 다음으로
제안하고 멈춘다. 원문을 수정하거나 새 PRD를 만들지 않는다. **리뷰와 문서 수정**을 함께 요청한 예시는
대상 파일과 허용한 수정 범위(예: 문장·링크 교정)를 명시한다. 제품 목적·범위·정책의 변경은 제안으로 남기고,
승인된 수정만 기존 위치에 반영해 수정 내역을 보고한다. 두 경우 모두 개발을 별도로 요청하지 않았다면 시작하지 않는다.

탐색 산출물의 양식·절차는 기반 스킬을 따른다. 기존 조사 자료는 현재 위치에서 활용하고, 새로 저장한
탐색 결과는 실제 경로를 PRD에서 연결한다. 덱이 별도 탐색 템플릿·고정 파일명을 만들거나 PRD에 전체 내용을 복제하지 않는다.
제품 탐색의 실험 계획과 superpowers의 개발 구현 계획을 구분한다. 페이지 추가 없이 기존 기획 페이지에 반영하는 안이며,
기본 5쪽·부록 3쪽은 여전히 검토 초안이다.

## Approaches

초안과 기존 본문에서 비교한 방향은 파일별 설명을 기본 경로에 두고 문서 분리 조건을 추가하는 방식이었다.
파일 위치는 명확하지만 기반 스킬의 양식과 역할을 덱이 다시 정하게 되고, 적용 전에 내부 구조를 공부해야 했다.

채택한 방향은 요청 중심 기본 가이드와 참조 부록이다. 사용자는 이 방향 하나를 승인했다.
기본 가이드는 독자가 맡길 작업 기준으로 나누고, 서로 겹치는 파일 중심 부록은 합친다.
기존 본문을 그대로 두고 사이드바만 바꾸는 방식은 중복과 옛 규칙을 남기므로 채택하지 않는다.
독자가 확인할 결과와 스킬 간 연결에 집중하며, 내부 형식은 공식 원문으로 연결한다.
이 선택은 재논의하지 않는다. 아래 세부 구성과 판정 기준은 이번 리뷰에서 구체화한 제안이다.

## 문서와 역할

- 새 PRD: docs/product-specs/PRD-[product-name].md. 폴더는 덱의 선택, 파일명·양식은 create-prd.
- 기존 PRD·기술 문서: 수정 요청 범위에서 현재 위치를 갱신하고 AGENTS.md에서 연결. 신규 기술 정보는 루트 README.
- 개발 산출물: superpowers의 specs·plans·임시 ledger 경로와 절차 유지.
- 앞서 정한 실행 선호(subagent-driven-development, 도구가 없으면 executing-plans)는 유지한다.
  이를 덱이 추가하는 공통 규칙으로 AGENTS.md마다 강제 복제하지 않는다. 이미 지정된 선호로 인계하고,
  실제 사용 조건·작업 분해·리뷰·완료 절차는 설치된 스킬이 판단한다. 작업들이 강하게 결합됐으면
  도구 존재만으로 SDD를 선택하지 말고 스킬의 적용 조건에 맞게 계획을 구성한다.
- PRD에서 이번 범위를 개발 설계로 넘기고, 지속할 제품·기술 사실을 구현·최종 수정과 함께 갱신한다.
  구현 완료와 대상 환경에 제공한 상태는 구분한다.
- _baseline.md는 독자·범위·근거·최소 연결 원칙의 위치를 남긴다. 본문의 운영 절차를 복제하지 않는다.

## 페이지 구성

기본 가이드: installation → project-setup → product-requirements → workflow → updates-and-handoff.
부록: agents-md → design-and-plans → paseo-agents.
기본 가이드 5쪽은 설치·적용·기획·개발·재개라는 서로 다른 요청을 맡으므로 구분한다.
부록은 지침 로딩, 문서 역할과 수명, 선택적인 Paseo 사용의 세 질문으로 줄인다. 기존 페이지 수를 맞추려고 절을 남기지 않는다.
index는 역할·독자·출발점·구성도만 보여 준다.
각 기본 페이지는 상황 → 요청문 → 받을 결과 → 확인할 핵심으로 작성한다.

| 페이지 | 남은 편집과 독자가 확인할 결과 |
|---|---|
| installation | superpowers・pm-product-discovery・pm-execution의 설치·버전·실제 스킬 확인을 안내한다. 읽을 수 없는 스킬·자동 로딩 미확인을 구분한다 |
| project-setup | 기존/신규 요청을 재사용한다. 문서 연결만 요청하면 탐색·첫 PRD 작성·환경 설치로 확대하지 않는다. PRD가 없으면 기획 요청으로 연결한다. 신규 세팅 요청은 필요한 제품 탐색·첫 PRD·승인된 최소 실행 환경까지 포함한다 |
| product-requirements | 아이디어 탐색, 첫 PRD 작성, 기존 PRD 리뷰만/리뷰와 문서 수정의 요청·결과·멈출 지점을 구분한다. 탐색 결과의 근거·가정·실험 판정 기준을 확인하고 필요한 맥락을 create-prd에 넘긴다. 스킬의 파일명을 유지하고 허용한 수정만 기존 경로에 반영하며 가정·미결정을 구분한다. 기획만 요청하면 개발 설계·계획·구현을 시작하지 않는다 |
| workflow | 개발 요청 → 접근법·설계 승인 → 계획 리뷰·확인 → 구현·검증 결과 확인. PRD 승인으로 기술 설계 승인까지 끝났다고 가정하지 않는다 |
| updates-and-handoff | 요구 변경·문서 갱신·같은 폴더 재개·다른 폴더 인계. 미추적 파일과 Git 제외 기록까지 대조하고 끝난 작업을 반복하지 않는다 |
| agents-md | 지침 로딩과 문제 해결. 짧은 연결 예시와 하위 지침의 적용 범위를 설명한다. 작동하는 import를 보존한다 |
| design-and-plans | 제목을 문서 역할과 수명으로 바꾼다. PRD·현재 기술 문서와 작업별 spec·plan·ledger의 차이, 읽기·갱신·보존을 한 페이지에서 설명한다. design-docs의 유효한 예제를 이곳으로 통합하고 중복은 제거한다 |
| paseo-agents | 선택 부록. 프로필·작업 폴더 연결만 요청문에 남기고 스킬 내부 절차·반복 위임 규칙은 복제하지 않는다. 결합 실행은 미실측으로 밝힌다 |

`design-docs.mdx`와 `other-approaches.mdx`는 학습 페이지에서 없앤다. 다른 도구 조합·폴더 배치의 비교는
이 가이드의 실행에 필요하지 않으므로 별도 페이지로 유지하지 않는다. 필요한 공식 근거는 해당 설명 가까이에,
하위 AGENTS.md의 적용 범위는 agents-md에 둔다. 삭제 전 미커밋 내용에서 옮길 사실·예제와 제거할 옛 규칙을 대조한다.

합치는 페이지의 옛 URL은 기존 정적 이동 페이지에서 연결한다. design-docs는 design-and-plans로,
other-approaches는 design-and-plans로 연결하며 기존 monorepo 관련 매핑은 agents-md의 해당 절로 바꾼다.
기존 specs-and-design·monorepo-instructions·public-repositories 경로도 직접 새 목적지를 가리키게 해 이동 사슬을 만들지 않는다.
현재 본문·map·사이드바는 새 경로를 직접 사용한다. 남는 페이지의 옛 절 ID는 현재 들어오는 링크가 필요로 할 때만
유지하고, 폐기한 개념을 설명하는 빈 절·이동 안내를 본문에 쌓지 않는다. 외부의 모든 옛 절 주소 호환은 이번 완료 목표가 아니다.

새 프로젝트 세팅에서 작성한 PRD는 다음 기획 페이지에서 다시 만들지 않고 리뷰한다. 기존 확정 요구의 버그 수정은
PRD 재작성이나 제품 탐색 반복 없이 개발로 간다. 제품 결정을 바꾸는 경우에만 필요한 PM Skills와 사용자 결정으로 돌아간다.
기획·개발의 기반 스킬 조합은 PM Skills와 superpowers로 유지한다. Codex와 Claude Code는 둘 중 하나만 써도 된다.
변경 전후 동작과 구현·출시 여부는 기존 PRD의 관련 설명에 남기며, 새 상태 필드·요구 ID 체계를 도입하지 않는다.
예시는 `docs/product-specs/PRD-task-manager.md`의 CSV 한도 1,000건 → 5,000건을 사용하고,
5,001건은 제한 안내라는 관찰 기준으로 요청·결과를 연결한다. 예시 제품을 실제 구현하지 않는다.

## 검토에서 확인한 현재 상태

- _baseline·index·_deck·installation·project-setup은 새 방향의 부분 편집이 있다. 유효한 부분을 재사용하고 새 구성에 맞춘다.
- product-requirements·agents-md에는 overview·필수 제품 README·요구 ID 관리가 남아 있다.
  design-and-plans·workflow·other-approaches에는 작은 변경 파일 생략, ledger Git 추적, 별도 리뷰·수동 양식이 남아 있다.
- design-docs의 기능 수 기반 분리, agents-md의 기존 지침 삭제·시작 줄만으로 로딩 확인,
  Paseo의 내부 절차 반복도 수정 대상이다. Claude Code 로딩 확인은 공식 `/memory` 안내와 대조한다.
- updates-and-handoff.mdx는 아직 없지만 sidebar·map·본문이 참조한다. 현재 상태를 사이트 검사 완료로 표시하지 않는다.
- pre-edit-anchors.json은 본문 9쪽의 기존 절 ID 80개다. 재개 시 소스 대조에서 모두 남아 있음을 확인했다.
  이 목록은 이제 이동·삭제 영향 확인 자료다. 80개 전부를 유지하는 검증은 하지 않으며 현재 참조와 이동 목적지의 정합성을 검사한다.

## 검증과 완료 조건

의미 리뷰에서는 기본 페이지의 요청문을 실제 스킬의 조건과 대조한다. 기존 PRD 존재/부재, 빈 프로젝트의
문서만 준비/실행 환경 포함, 기존 요구의 버그/제품 요구 변경, 계획까지만/승인 후 실행, 같은 폴더/다른 폴더 재개를
각각 확인한다. 아이디어 탐색만/PRD까지 요청, 탐색이 필요 없는 확정 요구, 실험 계획/실제 검증 결과의 구분도 확인한다.
기존 PRD 리뷰만/리뷰와 문서 수정 요청은 파일 변경 여부와 허용된 수정 범위까지 대조한다.
삭제 대상은 baseline·본문·코드 블록·이동 매핑을 함께 검색해 의미로 판정한다.

설계·계획만 수정한 승인 전 단계는 diff와 참조 경로를 검증한다. 승인 후 본문 편집을 마치면
`git diff --check`, sidebar·map 소스 대조, `npm run check` 한 번과 변경한 리다이렉트 목적지의
렌더 결과 대조를 수행한다. 현재 내부 참조가 삭제한 파일·절을 가리키지 않는지 확인한다.
기존 클라이언트 리다이렉트의 목적지 매핑을 바꾸므로 대표 1~2개 경로에서 실제 이동·절·query 보존만 브라우저로 확인한다.
페이지 구성 변경 자체를 이유로 덱 전체를 브라우저로 순회하지 않는다. 새 테스트 프레임워크·D2는 추가하지 않는다.
기존 컴포넌트·표·Steps로 충분하다.

이번 작업은 콘텐츠 편집이다. 저장소의 검증 지침이 스킬의 일반 코드 TDD·커밋 예시보다 우선한다.
작업별 의미 검토는 항상 수행하며 별도 작업 리뷰어는 위 실행 스킬 조건을 따른다. 전체 빌드를 작업마다 반복하지 않는다.
지속할 결정은 관련 본문 작업에서 본문·baseline에 반영해 통합 검증과 최종 전체 변경 리뷰의 대상에 포함한다.
최종 리뷰에서 새로 생긴 결정도 해당 수정과 함께 지속 문서에 반영하고 필요한 검증·리뷰 절차를 따른다.
최종 리뷰가 끝난 뒤 처음으로 지속 문서를 갱신하는 순서로 미루지 않는다.

계획의 Task 4는 통합 검증과 최종 리뷰 자료 준비까지 맡는다. 최종 전체 변경 리뷰·수정 처리·임시 기록 정리는
일반 구현 Task 밖에서 주 에이전트가 실행 스킬에 따라 수행한다. Task 4 담당자는 리뷰어를 생성하거나 workspace를 삭제하지 않는다.
주 에이전트는 Task 4까지의 완료 기록 후 전체 미커밋 diff·미추적 원문·검증 증거를 최종 리뷰에 넘긴다.
모든 작업과 최종 리뷰·필요한 수정 및 검증을 마치고, 판단·검증 결과·남은 제한을 최종 보고에 확보한 뒤에만
이번 임시 기록을 정리한다. 무커밋 상태를 완료 커밋으로 기록하지 않으며 승인 대기 중에는 기록을 보존한다.

## 구현에 맡기는 것

절 제목·문장·예제 길이는 독자의 중심 질문에 맞춘다. 페이지 통합 후 중복 설명은 제거한다.
참조 중인 절의 연결은 새 구성에 맞추되 기존 문서 모양을 유지하는 수단으로 쓰지 않는다.
기본 경로에서 외부 자료를 필독하게 하지 않고, 공식 사실은 해당 문장에 근거를 연결한다.
기존 공식 링크(superpowers 2ce8aa15d05bd57213e6f746f953aafb7ded7a8b,
PM Skills 07b34f64ee828df08953f505b7f747aef85ae7c6)는 설치 원문과 맞는 주장에만 쓴다.
버전 표와 추가 규칙의 설명은 근거·연결 조건이며 기반 스킬의 새 양식으로 제시하지 않는다.
설치·에이전트 간 실행을 실측했다고 쓰지 않는다.
